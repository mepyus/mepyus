# VectorFL Paper Pilot Scope And Merge Path v0

## why it was split as `weekend`
`weekend` was used as a scope lock, not as a permanent branch identity.
The point was to keep the first proof narrow enough that the system would actually close one loop instead of diffusing into more architecture, more pages, or more metaphors.

In other words:
- `weekend` means constrained pilot pressure
- not throwaway experiment
- not separate product line

## what happens later
Yes, this is meant to be absorbed.
But the right word is less `merge` and more `promotion into canonical pilot state`.

The sequence is:
1. Prove the first thin loop.
2. Enact runtime write-back.
3. Exercise reopen.
4. Replace the partly synthetic issue-like sample with a truer external source record.
5. Promote the same artifacts from `weekend` naming into general `vectorfl_paper_pilot` naming.

## what should not be merged yet
- broad company ontology
- broad multi-program orchestration
- design-heavy expansion
- additional agent shells unrelated to the thin loop

## what is already canonical in spirit
- scenario-bearing material as the first input
- internal-first, external-ready loop
- cell contracts
- supervisor-readable reporting
- runtime write-back
- reopen as return, not cosmetic status

## practical rule
Until the truer external source record pass is complete, keep the scope name.
After that pass, promote the same seam into general pilot naming instead of starting over elsewhere.
