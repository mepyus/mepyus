# Integrated Engine Operating Methodology Direction v0

## 1. Purpose

이 문서는 통합엔진을 앞으로 어떻게 읽고 작업할지에 대한 방향지시서다.

이 문서는 즉시 구현할 전체 기능 목록이 아니다. 사용자가 제시한 `외부 가능성 -> 공간 재료 -> 목적 선언 -> 팀 숙성 -> 검증 -> 공간 환류` 시나리오를 앞으로 작업 전 참조할 지도처럼 고정하기 위한 문서다.

핵심 전제:

- 통합엔진은 단순 업무 자동화 시스템이 아니다.
- 공간은 단순 저장소가 아니라 입력, 해석, 라인 형성, 검증, 환류, 숙성이 반복되는 구조다.
- 작업자는 화면이나 코드를 수정하기 전에 시나리오 안에서 현재 위치와 이번 범위를 먼저 잘라야 한다.
- 지금 단계의 목표는 미래 CLI 자동 운영까지 성급히 구현하는 것이 아니라, 그 방향으로 갈 수 있게 기록과 구조를 쌓는 것이다.

## 2. Scenario Lock

기준 시나리오는 아래 흐름으로 읽는다.

1. 사용자가 외부에서 가능성을 발견한다.
2. 외부 자료를 엔진면으로 넣어 공간 재료로 만든다.
3. 사용자면에서 목적을 선언하고 팀을 구성한다.
4. 내부팀이 먼저 공간 안을 읽는다.
5. 외부 서치팀이 내부 해석을 바깥으로 확장한다.
6. 구현팀이 테스트 가능한 결과를 만든다.
7. 검증팀이 결과와 과정 전체를 다시 읽는다.
8. 엔진은 검증 자료를 다시 공간에 넣는다.
9. 공간은 결과뿐 아니라 과정 전체를 재료로 먹고 숙성된다.
10. 현재는 사용자가 운영 주체지만, 미래에는 CLI 운영 주체가 일부 붙을 수 있다.

이 시나리오는 북극성이다. 한 번에 전부 구현할 계획표로 읽지 않는다.

## 3. Three-Surface Reading

### 3-1. User Surface

사용자면은 `목적 선언 + 팀 운영 + 담당 배치`의 표면이다.

여기서 중요한 것은 재료를 깊게 읽는 일이 아니라, 무엇을 하려는지 선언하고 어떤 방향으로 팀을 붙일지 정하는 일이다.

핵심 단어:

- 목적
- 선언
- 팀
- 담당
- 운영

금지 오해:

- 단순 task board로 축소하지 않는다.
- 엔진 내부 inventory를 사용자면의 주된 언어로 만들지 않는다.

### 3-2. VectorFL Surface

벡터플면은 `중간 흐름 표면`이다.

사용자 작업이 공간 안에서 line, relation, gap, genealogy, ingress, reflux, pending 상태로 어떻게 드러나는지 보는 통로다.

핵심 단어:

- line
- relation
- gap
- genealogy
- ingress
- reflux
- 중간 흐름

금지 오해:

- 예쁜 line viewer로만 만들지 않는다.
- 팀/담당/작업 배치를 이 면의 주축으로 삼지 않는다.
- 엔진 조작면처럼 다루지 않는다.

### 3-3. Engine Surface

엔진면은 `공간 컨트롤 표면`이다.

외부 자료를 공간 재료로 넣고, 입력 상태와 파이프라인, 자산, 경고, 검증, 환류, 정비를 감시하는 면이다.

핵심 단어:

- 입력
- 처리
- 파이프라인
- 감시
- 환류
- 정비
- 컨트롤

금지 오해:

- 일반 admin dashboard처럼 만들지 않는다.
- 지금 없는 자율 실행 능력을 UI가 이미 가진 것처럼 고정하지 않는다.
- 사용자 목적 선언 역할과 섞지 않는다.

## 4. Work Loop

앞으로 통합엔진 관련 작업은 아래 순서로 시작한다.

1. 시나리오 안에서 현재 작업이 어느 장면인지 확인한다.
2. 이번 수정이 사용자면, 벡터플면, 엔진면 중 어디에 속하는지 정한다.
3. 지금 당장 손댈 한 단계만 자른다.
4. 이번에 하지 않을 것을 명시한다.
5. 작업 후 무엇을 했고, 왜 했고, 무엇을 보류했는지 기록한다.

이 루프는 방법론이 아니라 운영 자세다. 목표를 달성하는 특정 절차라기보다 길을 잃지 않기 위한 방향 장치다.

## 5. Current Non-Goals

현재 단계에서 아래는 보류한다.

- CLI 자동 운영 주체 구현
- 화면에서 직접 repo 수정
- 엔진 자율 실행을 전제로 한 UI 고정
- 스크립트 생성/수정 자동 반영
- 시나리오 전체를 한 번에 구현하는 통합 대개편
- 사용자면, 벡터플면, 엔진면의 역할 혼합

단, 미래에 들어올 자리는 닫지 않는다. 현재 mock이나 placeholder는 확장 자리를 남기는 형태여야 한다.

## 6. Material Handling Rule

이 구조에서 결과만 재료가 아니다.

재료로 남겨야 하는 것:

- 외부에서 들어온 원본과 그 처리 흔적
- 목적 선언
- 팀 배치와 handoff
- 내부 읽기 결과
- 외부 보강 결과
- 구현 실험물
- 검증 판단
- 보류와 실패 이유
- 다음 단계 판단

작업 과정 자체가 공간의 기억이 된다. 따라서 보고서, close-out, checklist, 판단 기록은 단순 회의록이 아니라 환류 가능한 공간 재료로 취급한다.

## 7. Pre-Work Checklist

통합엔진을 건드리기 전 최소한 아래를 확인한다.

- 이 작업은 시나리오의 어느 장면인가?
- 이번 수정은 사용자면, 벡터플면, 엔진면 중 어디인가?
- 지금 잠가야 할 큰틀은 무엇인가?
- 이번에 아직 하지 말아야 할 것은 무엇인가?
- 결과뿐 아니라 과정 기억이 남는가?
- mock이 미래 확장 자리를 닫고 있지 않은가?

## 8. One-Line Lock

통합엔진 작업은 시나리오를 루트로 삼아 현재 위치를 찍고, 다음 목표만 잘라 움직이며, 그 과정 자체를 다시 공간의 재료와 기억으로 축적하는 방향으로 진행한다.
