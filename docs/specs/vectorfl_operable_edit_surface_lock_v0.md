# vectorfl operable edit surface lock v0

## purpose

Surface-only Paperclip adoption is not satisfied by showing organs and case flow.
The operating surface must expose edit-oriented page classes where operators can:

- re-assign the current organ
- revise next-hop preference
- edit ROLE / HANDOFF / CAUTION / RETURN bundle text
- attach or reserve future external teams

This lock keeps VectorFL core unchanged while adding those edit surfaces at the page-class level.

## locked page classes

### case routing page

- class:
  - work routing / assignment editor
- role:
  - edit current organ placement
  - revise preferred next organ
  - inspect and carry governance restrictions
  - attach external resource/program teams

### organ registry page

- class:
  - organ management / extension registry
- role:
  - inspect enabled organs
  - expose extension slots for future teams
  - keep bundle grammar visible before runtime expansion

### organ editor page

- class:
  - operable organ editor
- role:
  - edit ROLE / HANDOFF / CAUTION / RETURN bundle text
  - inspect current status
  - expose team-slot attachment points

## non-goals

- no backend persistence
- no canonical object change
- no governance semantics change
- no issue/agent/company ontology import

## page-grammar principle

These pages exist because Paperclip's value is not only list/detail display rhythm.
Its deeper value is the presence of genuinely operable pages.

VectorFL must therefore not stop at:

- case list
- case detail
- organ detail

It must also expose:

- routing editor
- registry/extension page
- organ editor

while keeping current-reading, governance, and trace canonical in the core.
