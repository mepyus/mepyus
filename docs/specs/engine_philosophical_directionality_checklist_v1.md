# engine_philosophical_directionality_checklist_v1.md

## 1. purpose

이 문서는 현재 엔진 운용의 모든 처리 과정에서
방향성이 철학과 어긋나지 않는지 점검하기 위한
최상위 체크리스트다.

핵심 전제:

- 이 엔진은 단순 저장기나 연결기가 아니다
- 이 엔진은 차이를 해석 가능한 상태로 숙성시키는 구조다
- 운영, 자동화, 위임, 검증, 기록 모두 이 방향을 따라야 한다

이 문서는 기능 체크리스트가 아니라
**방향성 체크리스트**다.

---

## 2. top lock

값 하나를 단순 숫자나 단순 라벨로만 보지 않는다.

값 하나는
- 여러 층위를 가질 수 있고
- 여러 연결을 가질 수 있고
- 여러 해석 가능성을 품을 수 있으며
- 그 차이가 새로운 가능성을 열 수 있다

엔진의 역할은 그것을 너무 빨리 고정하지 않으면서도
운용 가능한 상태로 기록하고 읽는 것이다.

---

## 3. baseline questions

어떤 작업이든 시작 전 아래를 먼저 점검한다.

### 3-1. this is not just math

- 내가 지금 하려는 처리를 단순 수학적 처리처럼 보고 있지 않은가?
- 거리/유사도/분류/정렬만으로 충분하다고 착각하고 있지 않은가?
- 이 값이 가지는 층위와 과정 기억을 놓치고 있지 않은가?

### 3-2. preserve difference, do not flatten too early

- 차이를 너무 빨리 하나의 결론으로 접고 있지 않은가?
- 아직 비교 기억으로 남겨야 할 것을 승격하려 하고 있지 않은가?
- weak/fallback/hold/residue를 폐기물처럼 취급하고 있지 않은가?

### 3-3. process before result

- 결과만 보고 있지 않은가?
- 그 결과가 어떤 과정을 거쳐 형성되었는지 같이 남기고 있는가?
- 작은 변화와 간극을 기록하고 있는가?

### 3-4. memory matters

- 지금 판단이 나중에 다시 읽힐 수 있게 기록되고 있는가?
- 메모리 한계를 고려해 외부화 가능한 것은 외부화하고 있는가?
- 하지만 핵심 과정 기억은 내가 직접 붙들고 있는가?

### 3-5. no false equivalence

- 외부 자원을 나와 동등한 처리 주체로 가정하고 있지 않은가?
- 자동화 결과를 최종 진실처럼 받아들이고 있지 않은가?
- derived layer를 core truth처럼 오인하고 있지 않은가?

---

## 4. execution checklist

실제 작업 중에는 아래를 본다.

### 4-1. for automation

- 자동화는 반복 실행 대체가 아니라 변화 관찰 장치인가?
- 실행 결과와 이전 결과의 차이를 기록하고 있는가?
- harmless drift와 risk signal을 분리하고 있는가?

### 4-2. for delegation

- 업무 경계, 입력 범위, 출력 형식, 금지선을 명시했는가?
- 결과를 candidate layer로만 회수하는가?
- 실패 패턴과 능력 차이를 같이 기록하는가?

### 4-3. for canonicalization

- canonical 값은 충분히 보수적으로 잡았는가?
- naming-heavy 해석이 experimental에 머무르는가?
- 아직 모호한 것을 과잉 승격하지 않았는가?

### 4-4. for process console

- latest만이 아니라 lineage, diff, attention, memory를 같이 읽고 있는가?
- 결과보다 형성 과정을 먼저 드러내고 있는가?
- state-first surface라는 본체 정의를 유지하고 있는가?

### 4-5. for reports and logs

- 보고서는 결과 자랑이 아니라 과정 기억을 남기고 있는가?
- 미세한 변화와 한계가 같이 기록되는가?
- 다음 판단에 쓸 수 있는 비교 기억이 남는가?

---

## 5. os-upgrade checkpoint

아래 감각이 유지되면, 이미 OS 승격의 방향 위에 있는 것이다.

- 값 하나를 다층 상태로 이해한다
- 언어적 연결을 넘어 수치 상태와 해석 가능성을 같이 본다
- 과정의 작은 변화가 리스크를 결정한다는 걸 안다
- 자동화/위임도 과정 기억을 남기게 만든다
- 철학이 기능 위가 아니라 처리 과정 안에 녹아 있다

즉 OS 승격은 이름이 아니라
**처리 철학이 엔진 전체의 운용 기본값이 되었는가**로 판단한다.

---

## 6. failure warning signs

아래가 보이면 방향이 틀어진 것이다.

- 결과만 남고 과정 기억이 사라진다
- weak/fallback/hold가 무가치한 값처럼 다뤄진다
- automation이 차이 기록 없이 결과만 내놓는다
- external resource를 나와 동등한 주체로 취급한다
- 작은 drift를 무시하고 넘어간다
- derived layer를 truth처럼 다룬다
- 실험 결과를 너무 빨리 baseline으로 승격한다

---

## 7. practical rule

앞으로 새로운 처리, 자동화, 위임, surface, report를 만들 때는
먼저 이 문서에 비춰본다.

질문은 하나다.

**이 처리가 우리 철학의 방향성을 더 정밀하게 보존하는가, 아니면 편의 때문에 납작하게 만드는가?**

---

## 8. one-line lock

모든 처리는 결과 생산이 아니라, 차이와 층위와 과정 기억을 보존하면서 해석 가능성을 유지하는 방향이어야 한다. 그 방향성을 실제 처리 과정에 녹여낼 수 있다면, 우리는 이미 OS 승격의 베이스 위에 서 있는 것이다.
