# Integrated Engine Product Surface Reframe v0

## 1. Verdict
PASS_WITH_NOTE

## 2. Purpose
This note locks the product-surface direction for the current integrated-engine UI. The goal is not a redesign from zero. The goal is to make the current one-handler operating surface easier to use by foregrounding one current package, separating event movement from content judgment, compressing support into digest cues, and keeping deep detail in inspector paths.

## 3. Current Problem
The current surface already has User / VectorFL / Engine projections, slot architecture, and a one-handler package. It still feels too close to verification mode when many process layers are visible at once:

- the current package is present but competes with lifecycle, queue, route, and support panels;
- event movement is not visually separate from content judgment;
- support panels can become a second front surface;
- deep trace / packet / route detail remains reachable, but some of it appears too early.

## 4. Product Surface Rule
The default screen should answer four questions in order:

1. What is the current package/object?
2. What just happened?
3. What compact cues help the current judgment?
4. What deeper material can be inspected intentionally?

## 5. Target Structure
### Current package/object
The center slot remains the main reading location. Each surface projects the same package differently:

- User: purpose, scope, status, next valid action, short reason.
- VectorFL: interpreted object, state, evidence, blocker/open edge, next route reason.
- Engine: ingest target, process stage, validation, return/redeposit, output meaning.

### Activity rail
The activity rail is a thin event layer. It may show sent/returned/pending/hold/failure/reroute movement, but not deep payload.

### Digest support
Support becomes a compact cue layer, not a second dashboard. It should carry warning, drift, evidence, trace, route, and not-done summaries.

### Inspector
Inspector holds full return records, route lists, line atlas, packet formation detail, provenance/trace, team configuration, and legacy mock surfaces.

## 6. Boundaries
This policy does not authorize:

- second handler expansion;
- team dashboard expansion;
- bridge automation;
- upper/lower unification;
- promotion or canonical redeposit;
- replacing the current shell with a new shell.

## 7. Validation
The policy stays within one-handler scope. It reduces same-process/same-projection confusion by keeping the process shared underneath while making front projection surface-specific and lower-density.
