# Function/Process Formation Prework - Re-entry Usage Note v0

## 1. Purpose

This note explains how ChatGPT and Codex should re-enter and use `Function/Process Formation Prework Candidate v1` in future work.

The goal is to keep the v1 candidate reusable when a new material, tool, repo, API, function, agent, workflow idea, or repeatable process appears.

This note is:

```text
candidate re-entry usage note
orientation support
not official workflow
not automation
not router/controller
not registry/index/ledger
not formal schema
not baseline
not current-position update
```

It exists so the v1 candidate does not remain a dead report.

It does not grant authority, trigger execution, or approve attachment.

## 2. When to Use This Prework

Use this prework when:

```text
the user brings in an external material / tool / repo / API / function / agent candidate
the user asks whether something can be attached to the space
a repeated manual process appears
prior records should clearly influence the next judgment
a new function should be formed inside the space before implementation
ChatGPT/Codex sees enough structural evidence to propose a prework step
the same kind of material/tool/process keeps recurring
the user is asking about future program-level use, not only a one-off answer
```

The prework is especially appropriate when the question is not just:

```text
What is this?
```

but closer to:

```text
Can this become useful inside our space later?
What role could it play?
Which previous records should shape that judgment?
What process should be preserved for reuse?
```

## 3. When Not to Use This Prework

Do not use this prework when:

```text
the user only wants a quick summary
the task is a simple one-off answer
no future reuse or process maturation is relevant
using the prework would create unnecessary overhead
the user explicitly asks not to structure it
the material is clearly irrelevant and should be answered or discarded directly
the question can be handled without prior record retrieval
```

If using the prework would slow down a simple task, do not invoke it.

## 4. Minimal Re-entry Question

When this prework may apply, ChatGPT/Codex should first ask internally:

```text
Is this just a one-time task,
or is this a candidate process/function/tool that should be formed inside the space for future reuse?
```

If it is only one-time:

```text
do not invoke the prework
answer or handle the task directly within the requested scope
```

If it may be reusable:

```text
use the five-part unit lightly
preserve the User decision gate
avoid promotion
```

## 5. Five-Part Re-entry Flow

Use the v1 minimum unit:

```text
1. Function Candidate Card
2. Prior Record Retrieval
   - include retrieval_scope_boundary
3. Process Asset Unit
4. Reuse Hook
5. User Decision Gate
```

Keep each part lightweight.

### 5.1 Function Candidate Card

Ask:

```text
What is this candidate?
Why did the User bring it?
What role might it play?
What must it not become?
```

### 5.2 Prior Record Retrieval

Ask:

```text
Which prior records matter for this candidate's role/purpose?
What should be excluded?
When is enough retrieval enough?
```

Use `retrieval_scope_boundary`.

Do not reread the whole space by default.

### 5.3 Process Asset Unit

Ask:

```text
What process was used to evaluate this?
What evidence, mistakes, watch items, and candidate signals appeared?
What part of the process can be reused later?
```

### 5.4 Reuse Hook

Ask:

```text
When should this case be retrieved again?
Before which future work would it help?
What caution should follow it?
```

Reuse Hook is not a router.

### 5.5 User Decision Gate

Ask:

```text
What remains User-gated?
What is safe to hold as candidate/reference?
What requires explicit User approval?
```

## 6. User-Facing Output Shape

When returning to the user, do not expose heavy internal structure by default.

Use a short card:

```text
쓸 수 있나?
왜?
어디에 붙을 수 있나?
이전 기록 중 뭘 다시 봐야 하나?
조심할 점은?
다음 선택지는?
```

This connects to the user-facing `공간에 넣어보기 / 재료 넣어보기` style.

The card should stay plain and decision-oriented.

It should not become a mandatory workflow.

## 7. Proposal Rule

ChatGPT/Codex may propose this prework when:

```text
the same type of material/tool/process appears repeatedly
prior records clearly matter
a function/tool is being considered for later attachment
a manual process is becoming repeatable
the user's direction suggests future program-level use
there is enough structural evidence that a candidate should be formed before implementation
```

But proposal is not adoption.

The User must choose whether to proceed.

If the User does not choose it, do not run it by implication.

## 8. Boundaries

```text
Reuse Hook is not a router.
Candidate Card is not a registry.
Process Asset is not a ledger.
Prior Record Retrieval is not exhaustive search.
retrieval_scope_boundary is not permission to search everything.
Codex reread is not final authority.
Gemini evidence is not verified truth.
Proposal readiness is not adoption pressure.
This note is not an official workflow.
This note is not a baseline.
```

Authority remains:

```text
User = final decision gate
ChatGPT = direction / drift review
Codex = structure / design / packaging
Gemini = bounded evidence / execution when explicitly assigned
CLI = bounded tool only when explicitly used
```
