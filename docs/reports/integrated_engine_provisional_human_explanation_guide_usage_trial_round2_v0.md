## 4. guide v0 five-step human explanation draft

This is a trial explanation, not final wording.

### 4.1 current operating status

The Gemini/Codex handoff is currently a documentation-only explanation trial. The Gemini mock material can be read as proposal/design clay, but it is still `proposal-only / needs Codex translation`. It does not become baseline, scaffold structure, runtime truth, or final wording just because it exists or looks useful.

### 4.2 protected authority / boundary

The protected boundary is that material must keep its authority state while it moves. Gemini can provide visual and conceptual material. Codex can translate that material against the current integrated-engine baseline, classify what is usable, what must be held, what can be carried forward, and what conflicts with current core. The user controls whether a later package opens for implementation, promotion, external harvest, or final wording.

Workspace ownership belongs in this boundary layer. `gemini/` material has proposal authority. `docs/reports/` can contain Codex-written canonical trial records when the user opens a documentation package. `runtime/views` and `runtime/manifests` remain closed here. This is not folder responsibility; it is artifact authority and collision prevention.

### 4.3 what remains closed

This handoff does not open scaffold edits, manifest shape changes, read-map changes, runtime binding, selected-object behavior, trace UI, extension promotion, wording patches, UI copy, final glossary, or external translation harvest.

Gemini mock elements that suggest supervisor queues, watcher recommendations, live manifest truth, bridge panels, line atlas as VectorFL center, team/role console dominance, or engine control-room authority remain outside current core. Some may be `carry-forward` material for later reread. Some are `reject / conflict` for the current baseline because they would cross protected surface, authority, or runtime boundaries.

### 4.4 possible re-entry / decision condition

A later route can open only through a scoped user decision. If the user opens a package, Codex can translate the relevant material again under that package's boundary. The result may still be reference-only, `hold`, `carry-forward`, `reject / conflict`, or `needs user decision`; translation does not equal promotion.

For example, visual rhythm from cards or badges can become reference material only after Codex confirms it preserves panel gravity and does not imply runtime truth. A supervisor/watcher/control-room idea would need much stronger promotion evidence and may still remain conflict for the current baseline.

### 4.5 what not to infer

Do not infer that Gemini material is canonical because it is useful. Do not infer that Codex translation is a simple relay or style cleanup. Do not infer that workspace ownership is folder ownership. Do not infer that `carry-forward` means approved future work, or that `reject / conflict` means a globally bad idea. Do not infer that the user is merely approving content; the user opens or keeps closed the next operating route.

Preserved:

- Hold means outside current core/package.
- Carry-forward means future-readable without commitment.
- Reject/conflict means current-baseline incompatibility, not global badness.

Thinness:

- Handoff explanation puts several classifications close together, so the distinction remains readable but dense.

Preserved:

- User decision is route-opening authority, not simple approval.
- No implementation or promotion opens without user-scoped package.

Thinness:

- If reduced to "user approves," package boundary disappears.

## 7. skeleton performance

Where the Gemini/Codex handoff skeleton worked well:

- It forced the explanation to name `proposal-only / needs Codex translation` before describing visual value.
- It placed workspace ownership in the protected boundary step, which helped prevent folder-owner flattening.
- It made closed scope explicit before describing carry-forward or reject/conflict.
- It kept user package-opening authority separate from Codex classification.

Where the skeleton remained thin:

- The `what remains closed` step became long because handoff contexts carry many prohibited routes.
- `carry-forward` and `reject / conflict` needed extra explanation after the five-step skeleton to avoid compression.
- `workspace ownership` still needed repeated "authority/provenance, not folder" language.

## 8. trial note

The guide v0 skeleton is reusable for Gemini/Codex handoff explanation, but it works because it stays explicit and procedural.

If turned into smooth collaboration language, the first losses would likely be:

- Gemini proposal material becoming design authority
- Codex translation becoming review or relay
- workspace ownership becoming folder responsibility
- carry-forward becoming roadmap
- reject/conflict becoming global judgment

Therefore this remains a guide usage trial, not final explanation copy.
