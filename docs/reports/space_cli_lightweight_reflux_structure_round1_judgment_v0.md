# Space-CLI Lightweight Reflux Structure Round 1 Judgment v0

## 1. structure judgment

The current structure is valid as a thought-experiment direction.

Working structure:

```text
user input
-> space input surface
-> source surface judgment
-> relevant line / axis / memory card retrieval
-> CLI work packet formation
-> CLI answer / execution / implementation
-> result recovery
-> native vs space-referenced diff reading
-> reflux memory formation
-> user-facing return
```

This structure is useful because it changes where judgment begins and where result value ends.

Plain CLI tends to answer or execute.

Space-referenced CLI first receives a bounded reading position, then returns material that can be reread and refluxed.

## 2. lightweight judgment

The space must not read every full source on every input.

Keep the lightweight reading order:

1. input routing
2. memory card retrieval
3. pointer-based source check
4. full source reading only when needed

This order is part of the structure's value.

If the space becomes a full-context dump, it loses the token and judgment advantage.

## 4. reflux memory state judgment

Round 1 supports the usefulness of these reflux states:

- `note_only`
- `reuse_hint`
- `risk_memory`
- `pattern_candidate`
- `hold_signal`
- `next_move_candidate`
- `deeper_probe_needed`

These states are not automatic execution triggers.

Especially:

```text
next_move_candidate != execute now
hold_signal != permanent rejection
pattern_candidate != baseline
risk_memory != proof of failure
```

The reflux state only changes what the next input reading should remember, check, or hold.

## 5. user-facing judgment

Do not expose the full internal diff and reflux structure by default.

Default user-facing return remains:

```text
쓸 수 있나?
왜?
다음엔?
조심할 점은?
```

Internal detail can be expanded only when needed:

- source surface confusion
- implementation pressure
- external material over-promotion
- neat PASS overtrust
- token/memory weight concern
- deeper probe requirement
