# saved-path curation pressure observation note under frozen page composition v1

## package status

complete for this turn

## observation frame

Current page composition stays fixed:

- core
  - `Operating`
  - `Explore`
  - `Search`
  - `Memory`
  - `Similar`
- companion
  - `History Companion`
- parked
  - `Saved-Path Curation`

This note does not reopen that map.

It only defines what kind of pressure would justify pulling `Saved-Path Curation` back out of parked status later.

## pressure 1. saved path accumulation pressure

- pressure level
  - medium-low
- current evidence
  - `Memory` already has a clear role for explicit saved paths
  - saved paths exist as a meaningful unit in the current operating set
  - but there is no strong evidence yet of volume or diversity that exceeds compact page handling
- why Memory still may be enough
  - `Memory` is still frozen as a compact selector and read point
  - current structure can hold explicit saved paths without needing a second organizational layer
- what would need to change before reopening candidate
  - repeated saved-path accumulation beyond quick scan
  - visible need to revisit saved paths across multiple sessions or themes
  - saved-path count/diversity high enough that compact ordering is no longer enough

## pressure 2. selection / revisit pressure

- pressure level
  - medium
- current evidence
  - there is a plausible future need to revisit, compare, or lightly reorder saved paths
  - current `Memory` can still select and inspect explicit saved paths without obvious overload
- why Memory still may be enough
  - `Memory` already covers the core job: inspect one explicit saved path and, if needed, move to `Similar`
  - there is not yet strong proof that users need a separate reread-and-compare surface rather than a compact saved-path page
- what would need to change before reopening candidate
  - repeated friction when finding an older saved path
  - repeated need to compare multiple saved paths side by side or by grouping
  - clear evidence that current selection flow is becoming too shallow or too crowded

## pressure 3. grouping / curation pressure

- pressure level
  - low
- current evidence
  - no strong observed requirement yet for collections, grouping, or curation layers
  - current discussion pressure is mostly structural plausibility, not demonstrated usage pressure
- why Memory still may be enough
  - `Memory` is intentionally explicit-path-only and compact
  - adding grouping too early would create an organization page before the actual organization pressure is real
- what would need to change before reopening candidate
  - repeated desire to cluster saved paths by topic, use, or reread intent
  - clear distinction emerging between “saved path selection” and “saved path curation”
  - evidence that saved paths are being retained faster than they can be reread inside current `Memory`

## pressure 4. drift risk if opened too early

- pressure level
  - high
- current evidence
  - the largest current signal is still semantic risk, not unmet page pressure
- why Memory still may be enough
  - keeping curation parked preserves the compact role of `Memory`
  - it also protects `Similar` from becoming an indirect curation workspace
- what would need to change before reopening candidate
  - pressure must become usage-driven rather than anticipation-driven
  - the need must be clearly separate from:
    - `Memory` selection
    - `Similar` seed activation
    - `History Companion` time-axis reading

## outcome

keep parked

## why parked still fits

- `Saved-Path Curation` is still the most natural adjacent candidate
- but the strongest current evidence is still “watch this pressure” rather than “open this page now”
- opening it early would more likely thicken `Memory` semantics than solve a proven page gap

## most important watchpoint

The key watchpoint is whether explicit saved paths start creating a real reread-and-reorganize burden that `Memory` can no longer hold without losing its compact selector role.
