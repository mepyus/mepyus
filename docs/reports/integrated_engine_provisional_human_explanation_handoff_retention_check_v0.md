## 2. fragile entry: `workspace ownership`

Decision:

- `retained_with_thinness`

What survived:

- Workspace was explained as authority/provenance and collision prevention.
- `gemini/`, `docs/reports`, `runtime/views`, and `runtime/manifests` were separated by artifact authority.
- The explanation explicitly said workspace ownership is not folder responsibility.

What almost got flattened:

- The use of workspace path examples still invites folder-owner reading.
- The explanation needed repeated boundary language to preserve authority meaning.

Which sentence order helped:

1. current handoff status
2. protected authority / boundary
3. workspace examples inside authority step
4. closed scaffold/manifest routes
5. explicit "not folder ownership" warning

What would mislead a reader if shortened too much:

- "Gemini owns proposal files and Codex owns reports" would erase canonicalization boundary and write authority.

Whether guide v0 was sufficient:

- sufficient, but still thin.
- The guide's boundary-first order worked, but workspace ownership remains the most fragile entry in handoff contexts.

## 3. fragile entry: `carry-forward`

Decision:

- `retained_with_thinness`

What survived:

- Carry-forward remained future-readable material without current operating authority.
- It was separated from implementation, promotion, and roadmap commitment.
- It was positioned after closed scope, which helped block approved-later reading.

What almost got flattened:

- Visual design material naturally feels like "something to use later."
- The phrase "later reread" can still sound like future scheduling if no-current-authority is omitted.

Which sentence order helped:

1. what remains closed
2. future-readable classification
3. no current authority
4. later user/package/gate requirement
5. not approved-later warning

What would mislead a reader if shortened too much:

- "Carry this visual idea forward" would sound like future implementation is expected.

Whether guide v0 was sufficient:

- sufficient for controlled explanation.
- It still needs the high-risk note's "preservation without commitment" language.

## 4. fragile entry: `reject / conflict`

Decision:

- `retained_with_thinness`

What survived:

- Reject/conflict stayed scoped to current baseline boundaries.
- It did not become global badness.
- It was separated from hold and carry-forward.

What almost got flattened:

- Handoff material includes visually attractive elements that conflict with baseline, so "reject" can sound like judging the design itself.
- The word conflict needs a named boundary every time.

Which sentence order helped:

1. protected baseline/surface/runtime boundary
2. closed scope
3. classification as reject/conflict for current core
4. possible future reread only if a valid package/gate opens
5. not global badness warning

What would mislead a reader if shortened too much:

- "Supervisor queue is rejected" would sound like the idea is bad, rather than incompatible with current core authority.

Whether guide v0 was sufficient:

- sufficient with note.
- The guide preserved the scoped conflict, but this entry should continue to name the exact boundary it conflicts with.

## 10. most protective parts of the five-step order

Most protective:

1. `current operating status`
   - prevented Gemini material from being read as already usable or canonical.
2. `protected authority / boundary`
   - kept Gemini, Codex, and User roles separate.
3. `what remains closed`
   - prevented visual reference material from opening scaffold, runtime, trace, or promotion paths.
4. `what not to infer`
   - stopped workspace/carry-forward/reject flattening after the explanation became easier.

Less protective but still necessary:

- `possible re-entry / decision condition`
  - useful, but it can sound like future scheduling if not paired with no-current-authority language.

## 11. remaining flattening pressure

Flattening pressure remains in three places:

- workspace examples still invite folder-owner reading.
- visual design value still pulls carry-forward toward "we will use this later."
- reject/conflict still sounds harsh unless the exact baseline boundary is named.

The guide reduces these risks but does not eliminate them.

## 12. handoff vs operating-mode stress test

Handoff explanation is a better stress test than operating-mode explanation for:

- `workspace ownership`
- `proposal-only`
- `needs Codex translation`
- `carry-forward`
- `reject / conflict`
- user package-opening authority

Reason:

- operating-mode explanation mostly protects closed state.
- handoff explanation must protect movement between agents, workspaces, material classes, and possible future routes.

This makes the handoff trial more likely to reveal authority and workspace flattening.

## 13. retention closeout

The guide v0 survived the Gemini/Codex handoff stress test.

It is reusable for controlled handoff explanation, but not ready to become final wording or external translation guidance.
