## 1. 핵심 오해

오늘 드러난 핵심 오해는 다음이다.

사용자가 원한 것은 engine language를 전부 human-facing language로 치환하는 것이 아니었다.

문제는 내부 언어를 적립한 것 자체가 아니었다. 문제는 그 내부 언어를 사용자가 직접 모두 읽어야 하는 전면 출력처럼 다루기 시작했다는 점이었다.

사용자가 필요로 한 것은:

- 어떤 언어가 어느 surface까지 노출되어야 하는가
- 성장하는 기록/기억/라인/연결/축을 사용자가 계속 다룰 수 있게 하는 고정 인터페이스가 왜 필요한가
- 내부 공간에서 나온 의미를 어떤 순서로 인간 가독 라인으로 세울 것인가
- 전체 내부 engine language를 외우지 않아도 운영할 수 있는 그릇이 어떻게 생겨야 하는가

이다.

## 2. 잘못된 방향

### 2.1 내부 언어를 전면 출력처럼 다룬 점

내부 언어 적립 자체는 필요했다.

하지만 그 결과를 사용자가 매번 직접 읽고 이해해야 하는 자료처럼 다루면, 통합엔진은 오히려 사용자의 부담을 키운다.

Engine language는 engine surface에서 충분히 드러나면 된다. VectorFL surface와 user surface에서는 각 surface 역할에 맞게 해석되어 올라와야 한다.

### 2.2 통합엔진을 설명 주제로만 다룬 점

통합엔진은 앱 구조나 설계 대상만이 아니다.

지금의 작은 지시, 판단, closeout, CLI 사용 여부도 다음 구조로 읽혀야 한다.

- 사용자면: 목적, 제약, 속도, 원하는 결과를 조직한다.
- VectorFL면: 내부 기록/기억/현재 자료를 읽고 무엇이 이미 있는지, 무엇이 부족한지 판정한다.
- 엔진면: 지금 필요한 최소 실행이 문서화인지, 내부 reread인지, 자료 증폭인지, CLI 보조인지 처리한다.

오늘의 흐름에서 이 프레임을 매 턴 충분히 적용하지 못한 것이 방향 혼선의 원인 중 하나였다.

### 2.3 인간용 보고 형식을 너무 빨리 앞세운 점

오늘 만든 bridge lexicon과 explanation guide는 유효한 보존 장치였지만, 그것이 최종 목적처럼 앞에 오면 안 된다.

올바른 순서는:

```text
내부 공간
-> 증폭
-> 인간 가독 라인
-> 연결
-> 축
-> 그 축에서 나온 고정 인터페이스
```

이다.

고정장치/그릇은 외부 UX template이나 보고 형식이 아니다.

그것은 기록/기억/라인/연결/축이 계속 자라는 상황에서도 사용자가 전체 내부 언어를 외우지 않고 공간을 다룰 수 있게 하는 운영 인터페이스다.

## 3. 수정 기준으로 잠글 것

### 3.1 1차 근거지

1차 근거지는 내부 기록/기억/저장/출력/데이터다.

외부 표현, CLI output, 보기 좋은 설명문, 일반 UX 용어가 먼저가 아니다.

먼저 봐야 하는 것은:

- 지금 repo 안에 무엇이 기록되어 있는가
- 어떤 line이 반복되고 있는가
- 어떤 line들이 연결되고 있는가
- 어떤 연결이 축으로 자라고 있는가
- 어떤 축이 사용자가 다룰 수 있는 interface를 요구하는가

이다.

### 3.2 자료 증폭의 목적

자료 증폭은 말을 더 많이 만들기 위한 것이 아니다.

자료 증폭은 내부 공간의 언어와 구조를 읽기 위한 것이다.

증폭된 자료에서 뽑아야 하는 것은:

- 반복되는 라인
- 라인 사이의 연결
- 연결이 만드는 축
- 축이 요구하는 surface별 노출 범위
- 사용자가 다룰 수 있는 고정 인터페이스의 최소 형태

이다.

### 3.3 번역의 위치

번역은 "외부 표현 치환"이 아니다.

번역은 내부 의미를 인간 가독 라인으로 세우는 일이다.

이때 중요한 것은 단어를 바꾸는 것이 아니라:

- 어떤 의미가 surface 밖으로 올라와야 하는지
- 어떤 의미는 engine surface 안에 남아야 하는지
- 어떤 의미는 VectorFL이 중재해서 올려야 하는지
- 어떤 의미는 user surface의 decision/operation 단위로만 보여야 하는지

이다.

### 3.4 line -> connection -> axis

라인은 단일 표현이나 단일 관찰이다.

연결은 라인들이 반복적으로 붙으며 생기는 관계다.

축은 연결이 충분히 반복되어 다음 작업의 기준이 되는 방향이다.

고정 인터페이스는 축 없이 만들면 외부 template이 된다. 축에서 나오면 성장하는 공간을 다루는 그릇이 된다.

### 3.5 surface별 언어 노출 밀도

Engine language / VectorFL language / user-facing language는 같은 밀도로 노출되면 안 된다.

기준:

- engine surface: 처리/실행/반환에 필요한 engine language가 충분히 드러난다.
- VectorFL surface: 내부 기록/기억/라인/연결/축을 읽고 중재하는 언어가 드러난다.
- user surface: 사용자가 운영/분배/결정할 수 있는 고정 interface 언어가 드러난다.

사용자가 engine 내부 언어 전체를 직접 외우고 운용해야 한다면, 그 interface는 실패다.

## 4. 앞으로의 처리 규약

작은 요청도 통합엔진 구조로 읽는다.

### 4.1 사용자면에서 먼저 읽을 것

- 목적은 무엇인가
- 제약은 무엇인가
- 속도/범위는 어느 정도인가
- 사용자가 원하는 결과는 문서인가, 패치인가, 판단인가, 실행인가
- 지금 열면 안 되는 것은 무엇인가

### 4.2 VectorFL면에서 읽을 것

- 내부 기록/기억/현재 자료에 이미 있는 것은 무엇인가
- 반복되는 line은 무엇인가
- line들이 연결되는 지점은 어디인가
- 연결이 축으로 자라고 있는가
- 사용자의 답답함은 내부 언어 부족인가, 노출 범위 문제인가, interface 부재인가

### 4.3 엔진면에서 판단할 것

지금 필요한 최소 실행은 무엇인가:

- 내부 reread
- 자료 증폭
- line/connection/axis 정리
- closeout
- CLI 보조
- 문서 작성
- 패치

이 중 CLI는 본체가 아니다.

CLI는 내부 구조 reread 뒤 부족한 표현, 확장, 외부 생성, 보조 실행을 맡는 실행기다.

## 5. CLI 위치 재정의

CLI는 통합엔진의 본체가 아니다.

CLI는 다음 조건 뒤에 붙는다.

1. 내부 기록/기억/현재 구조를 먼저 읽는다.
2. 무엇이 부족한지 VectorFL면에서 판정한다.
3. 사용자면에서 요청 범위와 금지선을 조직한다.
4. 그 뒤 필요한 경우 CLI를 보조 실행기로 붙인다.

Gemini CLI는 특히:

- 디자인 재료
- 표현 후보
- mock/proposal material
- 외부 확장 표현
- 다른 시각/언어의 가능성

을 만드는 데 쓸 수 있다.

하지만 Gemini CLI output은 직접 core가 되지 않는다. Codex translation / VectorFL mediation / user package-opening authority를 거쳐야 한다.

## 6. closeout

오늘 방향 수정의 핵심은 다음 한 문장이다.

통합엔진의 목적은 내부 언어를 전부 인간 언어로 치환하는 것이 아니라, 내부 공간에서 증폭된 line / connection / axis를 읽고, 그 축에서 사용자가 계속 다룰 수 있는 고정 인터페이스를 만드는 것이다.

이 문서는 그 방향을 다음 채팅의 시작 기준으로 잠근다.
