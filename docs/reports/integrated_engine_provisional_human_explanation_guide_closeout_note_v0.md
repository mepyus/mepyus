## 2. what this round locked

Locked as reusable provisional guidance:

```text
current operating status
-> protected authority / boundary
-> what remains closed
-> possible re-entry / decision condition
-> what not to infer
```

This order is now the preferred explanation structure for:

- current integrated-engine operating mode explanation
- Gemini/Codex handoff explanation
- S3 drift / reprocess / reflux explanation
- internal-to-human bridge explanation drafts

## 4. high-risk sequence findings

The high-risk note confirms that the risky entries need sequence protection:

| entry | sequence requirement |
|---|---|
| `workspace ownership` | authority/provenance before folder/path |
| `hold` | outside current package but preserved before "not active" |
| `carry-forward` | future-readable plus no current authority together |
| `reject / conflict` | scoped baseline conflict before reject language |
| `collision stop condition` | protected-boundary crossing before stop/error language |
| `watch keep` | observation-only before re-entry condition |

The common flattening pattern remains:

- `workspace ownership` -> folder owner
- `hold` -> backlog / unused
- `carry-forward` -> approved later
- `reject / conflict` -> bad idea
- `collision stop condition` -> error
- `watch keep` -> TODO / patch queue

## 5. what is now stable enough to reuse

Stable enough for controlled explanation:

- the five-step explanation order
- status-before-simplification rule
- authority/boundary before workspace/path examples
- closed-scope before re-entry condition
- explicit "what not to infer" ending
- separate skeletons for operating mode, handoff, and drift/reprocess

These are guide-level stable, not final-copy stable.

## 6. what remains fragile

Still fragile in actual use:

- `workspace ownership`
  - still needs repeated authority/provenance framing.
- `carry-forward`
  - still risks sounding like scheduled future work.
- `reject / conflict`
  - still risks global badness if the scoped conflict is not named first.

Also fragile:

- any shortened explanation that drops "what remains closed"
- any explanation that starts with a friendly substitute
- any explanation that treats hold/watch/carry-forward as ordinary project management labels
