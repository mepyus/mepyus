# Space External Tool Repo Attach Feasibility Report v0

## 1. Purpose

This report answers the second half of the user request:

- how the imported tool functions connect to our current space
- what is structurable now
- what should remain outside

## 2. Current Space Criteria Used

This pass used the current space as it already exists:

- lower input organ remains a distributed intake-digestion belt, not the upper operating surface
- lower-to-upper bridge remains supervisory and dependency-heavy, not automatable by default
- integrated-engine current operating surface already has:
  - user / VectorFL / engine separation
  - CLI-on-top operation
  - packetization precedent
  - return / deposit candidate surfaces
- package continuity already exists as a bounded notebook/session idea

This means:

- wholesale runtime replacement is the wrong direction
- attachability must be judged feature-first

## 3. Related Line Pressures In Our Space

Without naming final axes, the strongest current pressures are:

- request packetization
- bounded external-to-space adaptation
- retrieval / evidence access
- operator/runtime workflow shaping
- repeated completion / continuity loops
- permission / tool boundary discipline

## 4. Feature-Level Mapping

### 4.1 QMD -> Retrieval / Evidence Access Layer

Strongest attach path:

- local indexed retrieval sidecar
- CLI/MCP retrieval support for bounded document access
- evidence bundle support for user/VectorFL-side reads

Why it fits:

- our current input flow map explicitly says the evidence bundle gate is not a full automatic repository search engine
- QMD is narrow enough to fill retrieval, not replace the whole engine

Current judgment:

`strong attach candidate`

Bounded first use:

- retrieval support for imported references and internal markdown corpora
- not authority replacement
- not lower-organ replacement

### 4.2 OpenHarness -> Tool / Permission / Session Patterns

Strongest attach path:

- tool registry concepts
- permission checker concepts
- query/session boundary reading
- worker/session continuation lessons

Why it fits:

- our current space already has package continuity and actual worker-return precedent
- OpenHarness offers mature patterns for tool execution and permission framing

Why full attach is wrong:

- it would collide with our current integrated engine surfaces
- it is too broad to import as a whole without runtime replacement pressure

Current judgment:

`bounded pattern candidate`

Bounded first use:

- study and translate selected registry / permission / session boundary ideas
- do not import the full harness runtime

### 4.3 OMX -> Workflow Layer / Role Surface

Strongest attach path:

- workflow separation patterns
- clarification -> planning -> execution / completion staging
- durable local workflow state ideas

Why it fits:

- our current space already has packetization and surface separation
- workflow vocabulary can strengthen operator-facing request shaping

Why full attach is wrong:

- its runtime layer is tightly tuned around Codex and `.omx/`
- our current space already has its own operating layers and bridge constraints

Current judgment:

`bounded pattern candidate`

Bounded first use:

- borrow workflow decomposition ideas
- do not import team/ralph runtime wholesale

### 4.4 Ralph -> Persistent Completion Loop Pattern

Strongest attach path:

- repeated bounded completion loop
- append-only progress memory
- task-pass ledger pattern

Why it fits:

- our space already values append-only records and package continuity
- Ralph provides a narrow completion-loop pattern rather than broad harness replacement

Why full attach is wrong:

- it assumes a PRD-driven execution loop shape
- current space does not yet authorize direct completion-loop adoption as a default surface

Current judgment:

`bounded pattern candidate`

Bounded first use:

- compare against current package continuity / return-record / redeposit material
- treat as a follow-up loop reference, not a base runtime import

## 6. Structurable Next Set

If this package continues, the safest bounded structurable set is:

1. `QMD` as retrieval-side attach candidate
2. `OpenHarness` as tool/permission/session pattern mining candidate
3. `OMX` as workflow-surface pattern candidate
4. `Ralph` as completion-loop comparison candidate

This is a better next set than "which whole repo should we adopt?"

## 7. Validation

### What this pass verified

- imported repos can be split into attachable function surfaces rather than treated as monoliths
- our current space boundaries are strong enough to reject wholesale runtime import
- at least one repo (`qmd-main`) emerges as a near-term bounded attach candidate
- several repos emerge as pattern/reference candidates rather than repo-level adoption targets

### What this pass did not verify

- actual code integration
- runtime compatibility
- storage destination
- package notebook continuation
- implementation cost

## 8. Feasibility Verdict

`PASS_WITH_NOTE`

The requested analysis is structurally feasible and natural under the current orchestration package.

But the natural next move is:

- feature-level attach experiments

not:

- repo-level import
- runtime replacement
- broad architecture swap
