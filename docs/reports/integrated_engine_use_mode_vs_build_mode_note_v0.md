# Integrated Engine Use Mode vs Build Mode Note v0

Date: 2026-04-15

## 0. verdict

PASS

The current baseline should be used before more build work is started.

The baseline has enough structure to read the three manual scenarios, and the remaining issues are mostly wording or observation thinness rather than structural blockers.

## 1. why use observation matters now

The integrated-engine baseline has already passed:

- v1 candidate lexicon / protocol / interface alignment
- three low-intensity scenario structure checks
- Round 1 visual translation
- Round 2 bounded refinement
- Round 3 shared visual token extraction
- Round 4 render-contract audit
- Round 5 render-field inventory
- Round 6 empty-state and trace boundary notes

At this point, more building risks creating false precision.

Use observation is more valuable because it shows:

- whether the panels are readable in real scenario order
- whether support panels stay subordinate during use
- whether route readability works without trace UI
- whether wording confusion actually repeats
- whether held extensions are genuinely needed or only visually tempting

## 2. what the current baseline can do

Current baseline can support:

- manual user-origin request -> VectorFL -> engine -> return -> reflux reading
- manual VectorFL maturation signal -> user-organized follow-up -> engine return reading
- manual anchor drift -> reprocess / rewind reading
- central panel role separation across all three surfaces
- request / return / reflux separation
- compact route and connection-record support
- documentation-level empty-state and trace boundary reasoning

## 3. what is still too early

Still too early:

- selected-object behavior
- selected route state
- side-inspection value rendering
- denser trace UI
- broader connection-record timeline
- runtime binding
- live manifest truth
- watcher / supervisor / bridge authority
- worker/process telemetry
- extension promotion

Reason:

- these require contracts beyond current scaffold-level render fields and would shift the work back into build mode before use has proven the need.

## 4. when wording-only refinement is allowed

Wording-only refinement is allowed when:

- the same confusion appears in more than one manual run
- the fix can be made without read-map, manifest, or panel changes
- the wording protects an existing boundary rather than adding a new behavior
- the change does not imply selected-object behavior, trace UI, runtime truth, or governance

Examples:

- clarify that request organization can shape follow-up signals
- clarify that support inspection is future/secondary
- clarify that engine return is validation-bound
- clarify that evidence history is compact trace support, not a live feed

## 5. why it is safe to use now

It is safe to use now because:

- all central panels remain legible
- route separation survives normal, follow-up, and drift loops
- support layers do not become authority
- empty states are not needed for current manual sample reading
- trace UI is not needed for current manual route reconstruction
- held extension axes are documented and gated

## 6. mode recommendation

Current mode:

- stop and use

Fallback mode:

- wording-only patch if repeated use-time confusion appears

Avoid:

- build mode
- extension promotion
- runtime binding
- trace UI implementation
