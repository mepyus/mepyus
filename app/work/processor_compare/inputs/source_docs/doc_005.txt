데이터 엔지니어링
팔란티어 개념 설명 - 온톨로지
라이크나우 2025. 12. 10. 11:10
팔란티어는 사실 기술보다도 주가로 인해 핫해서 자주 들어봤습니다. 항상 보면서 공부해야지.. 데엔으로서 알아봐야지.. 하던 그 팔란티어를 드디어 정리해봅니다.

결론부터 말씀드리자면, 팔란티어는 모든 데이터를 라벨링하고 라벨링된 데이터 사이의 관계도 라벨링합니다. 그러면 디지털 상에 현실의 정보를 고스란히 반영할 수 있다고 보죠. 이 디지털화 된 정보를 효율적으로 활용하여 현실의 여러 문제를 해결하겠다는 플랫폼 입니다. 어리둥절하죠? 이를 이해하려면 온톨로지 개념을 가볍게 먼저 짚고 시작해야겠습니다.

Ontology란?

데이터에 “의미와 맥락”을 부여해
현실 세계(조직·자산·사람·프로세스)를 그대로 디지털에서 재현하는 구조(=디지털 트윈)

온톨로지를 깊숙하게 이해하기 위해서는 다른 용어들도 많이 필요하지만 우선 이렇게만 이해해도 좋다고 생각합니다. 현실의 모든 것을 객체화하고 해당 객체 사이의 관계는 링크로 표현합니다. 현실에서 일어나는 모든 사건은 액션으로 표현하여서 디지털화 시키는 개념입니다. 현실을 그대로 반영한다는 의미로 디지털 트윈이라고 표현하기도 합니다. 말만 들으면 참 방대한데요, 이 방대한 작업을 쉽게 해내기 위해서 지난 20년 동안 노력한 회사가 팔란티어라고 보면 됩니다.

아직도 이해가 안가신다면 우선 반대로 접근해봅시다. 현실의 모든 것을 디지털화 시키고 싶다면 어떤 작업을 거칠까요?

"블로그 글을 작성하고 있는 나" 를 설명하기 위해선

나(User)
노트북(Device)
카페(Location)
블로그(Blog)
티스토리(Platform)
작성 중인 글(Post)
글쓰기라는 행위(WriteEvent)
등으로 쪼개어 생각할 수 있습니다. 그리고 이 개념은 아래와 같이 서로 연결할 수 있죠.

나는 카페에 있다
내 노트북은 카페에 있다
글은 내 블로그에 있다
내 블로그는 티스토리에 속한다
나는 글을 작성한다
나는 노트북을 사용한다
이렇게 현실을 나노단위로 쪼개야 디지털에 반영할 수 있지 않을까요? 이런 식으로 디지털에 현실의 쌍둥이 버전을 만드는 과정이 팔란티어의 온톨리지를 구축하는 과정입니다.

우선 팔란티어는 왜 이 "온톨로지"를 중요시 여기는지만 짚고 넘어갑시다.

1. 현실의 문제점
지금까지 기업의 데이터 시스템은 대부분 아래와 같이 다뤄집니다.

시스템 별로 데이터를 따로 저장함 (사일로)
서로 다른 관점으로 존재함 (서비스, 마케팅, 로그, 결제 등)
이렇게 수많은 데이터는 존재하지만 이 데이터들 사이의 관계가 끊어진 상태임
그래서 현실에서는 직장인들이 협업하여 이 정보들을 유기적으로 연결하여 사용해야합니다.

데이터 사이의 관계가 끊어져 있기 때문에 수작업으로 진행해야하는 경우도 허다하구요, 특정 부서에서 적용한 최적화 방법이 전체에게 적용되지 않는 방법이라 전사 적용이 힘들 수 있습니다.

만약 이 모든 데이터를 디지털 상으로 그대로 본뜨듯이 옮기고

현실에서 문제였던 데이터 사이의 단절을 해결하기 위하여 온톨로지 개념을 입혀서 데이터들에 라벨링 즉 의미를 부여한다면요?

이들을 서로 연결하여 융합적으로 바라볼 수 있다면 데이터를 더 잘 활용할 수 있지 않을까요?

그러니까, 온톨로지를 사용해서 데이터에 개념적으로 접근하면 현실의 문제점을 해결할 수 있는거죠.

2 . 핵심 개념 - Ontology
이제 온톨로지를 검색하면 나오는 개발자 관점의 접근도 살펴봅시다.

Ontology 구성
Object Type: 현실의 엔터티/이벤트
Property: 속성
Link Type: 관계
Action Type: 실제 행동(재할당·승인·스케줄 변경 등)
Ontology를 구성하는 Object / Property / Link / Action을 하나씩 살펴보면,
팔란티어가 ‘현실을 디지털로 반영한다’는 말을 왜 강조하는지 자연스럽게 이해됩니다.

2-1) Object Type

앞서 예로 들었던 나(User), 노트북(Device), 카페(Location), 블로그(Blog) 같은 것들이 전부 Object Type입니다.

데이터 입장에서 보면 사람, 카페, 콘텐츠 같은 테이블이 Object Type으로 승격되는 구조라고 볼 수 있습니다.
Foundry 내에서 온톨로지를 만드는 과정을 해보면 더 직관적인 이해가 가능한데요, Pipeline Builder에서 만들어놓은 완성된 데이터인 Dataset을 Object로 지정하면서 Ontology를 만들 수가 있습니다.

여기서 중요한 점은 Object Type이 단순히 테이블이라는 의미를 넘어서,
비즈니스적으로 중요한 개체를 ‘하나의 단위’로 정의하는 컨테이너 역할을 한다는 것입니다.
Object Type 안에

데이터 품질 규칙
계산된 속성
보안 정책
연결된 액션
모델 결과
까지 통합할 수 있기 때문에 Object는 그 자체로 비즈니스의 최소 단위가 됩니다. 이게 기존 데이터모델링과 가장 다른 점입니다.

2-2) Property

Object 안에 포함된 컬럼이 Property입니다.

Cafe라는 Object Type이 있다면

cafe.name
cafe.location
이게 Property죠. 단순 컬럼으로 생각해도 좋지만
Functions(타입스크립트/파이썬)로 계산된 값도 Property가 될 수 있습니다.
예를 들어

사용자의 churn_score
콘텐츠의 retention_lift
재생 실패율
같은 계산된 비즈니스 지표도 Property가 됩니다.

즉, Property는 실제 데이터의 컬럼 + 계산된 지표까지 포함하는 더 넓은 의미의 속성입니다.

2-3) Link Type: Object 사이의 관계 (RDB의 FK와 다르다)

현실 세계는 개체들이 서로 연결되어 있기 때문에 의미가 생깁니다.
Ontology는 이 현실의 관계를 Link Type으로 표현합니다.

나는 노트북을 사용한다              : User —[uses]→ Device
나는   카페에 있다                      : User —[located_at]→ Location
글은 내 블로그에 있다                : Post —[belongs_to]→ Blog
내 블로그는 티스토리에 속한다   : Blog —[hosted_by]→ Platform

Foundry에서는 위와 같이 세가지 방식으로 object 간에 관계를 맺게 해줍니다.

1) Object type foreign keys

한 Object Type 안에 다른 Object Type의 primary key가 포함되어 있을 때 사용하는 방식입니다.
현실에서도 “A 안에 B의 아이디가 들어 있다”는 형태라면 대부분 1:1 또는 1:N 관계죠.
가장 단순하고 직관적인 관계입니다.

예: Order 테이블 안의 user_id → User —[placed]→ Order

2) Join table dataset

두 객체가 서로 many-to-many 관계일 때,
중간에 두 객체의 primary key만 담긴 테이블을 이용해 관계를 표현하는 방식입니다.
관계 자체에 속성이 필요 없을 때 사용합니다.

예:
배우 ↔ 영화
User ↔ Genre

3) Backing object type

관계 자체에 속성(Property) 이 붙는 경우, 혹은 그 관계가 사실상 하나의 이벤트(Event) 로 취급되어야 하는 경우에는
관계를 단순 링크로 만들 수 없어서 아예 독립된 Object로 승격합니다.

예:
User가 Content를 시청(Watch)하는 행위
→ watch_time, device, timestamp 등이 필요
→ 관계가 아니라 WatchEvent라는 Object로 만들어야 함

이 세 가지 방식이 Foundry가 현실의 관계를 유연하게 모델링하는 기본 도구입니다.

여기서 중요한 점은 Link Type이 단순 join이 아니라는 점입니다.

Link Type은 한 번 정의되고 나면 단순히 두 테이블을 이어주는 것을 넘어, 아래 요소들에 적극적으로 활용됩니다:

그래프 탐색
관계 기반 검색 및 필터링
관계 기반 보안 정책(Purpose-based Security)
LLM이 관계를 따라 reasoning 하는 근거
ML 모델이 관계 경로를 feature로 활용하는 구조
즉, 관계는 단순한 데이터 연결선이 아니라
AI가 현실을 이해하고 추론하도록 만드는 의미의 연결선입니다.

Ontology에서 관계를 제대로 만드는 것이 중요한 이유가 바로 여기에 있습니다.

2-4) Action Type: 객체의 실제 행동이자 운영계 접점

현실에서는 모든 개체가 행동합니다.
글을 작성하고, 위치가 이동하고, 이름이 바뀌고, 주문이 승인되고, 재고가 보충되는 식이죠.

Ontology에서는 이 현실의 행동을 Action Type으로 정의합니다.

예를 들면,

나는 글을 작성한다                    : write_post
나는 카페를 옮긴다                    : update_location
나는 블로그 글 제목을 변경한다  : change_title
등이 있습니다.
이 Action들은 Ontology 내의 Workshop 등의 기능을 통해 UI 버튼으로 구현될 수도 있고 자연어로 처리될 수도 있습니다.
이는 단순히 데이터를 변경시키는 과정이 아니라 실제 운영 시스템에 적용되는 명령 그 자체로 여겨집니다.
실행되면 내부적으로 Function, 외부 API, 모델 호출 등과 연결되며 LLM 에이전트가 Action을 자동으로 실행할 수도 있습니다.

즉, Action Type은 데이터 레이어와 운영 레이어를 연결하는 팔란티어만의 핵심 구조입니다.

위에서 언급했듯이 지금까지의 데이터 시스템은 복잡했습니다.

데이터는 여러 시스템에 흩어져 있고
서로 연결되지 않았고
운영에서 발생하는 행동(Action)은 데이터와 완전히 분리되어 있었죠.
Object / Property / Link / Action 구조는
이 세 가지 문제를 한 번에 해결합니다.

Object – 현실의 개체가 디지털로 존재하고
Property – 그 개체의 모든 상태가 기록되고
Link – 개체 간의 관계가 그래프 형태로 의미 있게 연결되고
Action – 현실의 행동이 디지털 세계에서도 그대로 실행됩니다

이 네 가지를 합치면 현실과 1:1로 대응되는 디지털 트윈 세계가 만들어집니다.

그리고 이 디지털 트윈은 AI 모델과 LLM이 정확하게 reasoning 하고, 운영에 직접 영향을 주는 자동화(Action)를 할 수 있는 기반이 됩니다. 팔란티어가 말하는 온톨로지 중심 운영 시스템이 바로 이런 구조입니다
