## 5. Execution-to-Space Lane

Describe:
- Execution Layer
  - Hermes receives a bounded context packet and runs real work only within explicit permissions: allowed inputs, forbidden actions, output path, tools, mode/depth, return shape, and STOP conditions.
  - In a future Hermes-main stage, this layer may include company tasks, B2B workflows, content ops, customer response, local scripts, browser/file/terminal work, and approved automation, but it still does not own VectorFL authority.
- Run Trace Layer
  - Hermes returns a trace package: report, receipt, read/write scope, tools/actions used, errors/failures, outputs, WATCH, HOLD, and recovery recommendation.
  - The trace must distinguish task result from evidence, receipt, residue, candidate, and authority request.
- Recovery Gate
  - Codex classifies Hermes outputs as discard / receipt / residue / candidate / component / space_update_proposal / STOP.
  - Codex prevents raw output flood from entering VectorFL Space and blocks authority, memory, automation, cron, skill, config, baseline, registry, workflow, ontology, current-position, output_manifest, or local authority mutation pressure.
- Maturation Layer
  - Gemini receives selected batches of residue/candidates/components for broad comparison and naming.
  - Gemini may propose patterns, thresholds, labels, vessel refinements, or higher-level concepts; it cannot grant authority.

## 6. Minimal Hermes Context Packet

What Codex should give Hermes before a bounded run:
- task
  - One explicit mission statement with expected result and non-goals.
- allowed files
  - 1-5 explicit input paths by default; no sibling inspection, link following, or broad search unless separately approved.
- forbidden files/actions
  - Secrets, auth, state.db, .env, sessions, credential logs, Hermes memory/skills/config/cron state, AGENTS.md, SKILL.md, baseline, workflow, schema, registry, ontology, current-position, output_manifest, local authority surfaces, recurring automation, and real cron lifecycle commands.
- output path
  - One declared sandbox output directory and exact allowed output file names.
- mode/depth
  - IIC-selected depth: plain chat / simple answer / light review / full review / layer-shift / STOP; execution depth must remain bounded.
- return format
  - Required sections for report, receipt, WATCH, HOLD, failures, read/write scope, tools/actions used, and recovery recommendation.
- STOP conditions
  - Any vessel STOP halts the lane; especially authority pressure, memory/skill/config writes, automation/cron creation, promotion, broad search, and undefined file/action expansion.
- recovery target
  - Codex classification target: discard, receipt, residue, candidate, component, space_update_proposal, or STOP.

## 7. Hermes Return Contract

What Hermes should return after a run:
- report
  - Human-readable result, bounded by task scope, with evidence and limits.
- receipt
  - What ran, files read, files written, commands/tools used, exit status when relevant, output paths, and explicit non-actions.
- read scope
  - Exact files read, missing files, and files explicitly not read.
- write scope
  - Exact files created/modified and confirmation of no other writes.
- tools used
  - Browser/file/terminal/scripts/cron/no-agent/etc. as applicable, including whether any network or subprocess was used.
- errors/failures
  - Failures, missing inputs, partial results, fallback attempts, and whether execution stopped safely.
- WATCH
  - Visible risks: output flood, authority-language drift, recurrence pressure, evidence overclaim, role confusion, incomplete context.
- HOLD
  - Blocked actions: authority updates, baseline promotion, memory/skill/config edits, real cron, recurring automation, broad search, current-position/output_manifest, registry/schema/workflow/ontology.
- recovery recommendation
  - Hermes may suggest a classification, but Codex decides. The recommendation should be conservative: discard/receipt/residue before candidate/component, and STOP when authority pressure appears.

## 8. Codex Recovery Classification

| Class | Meaning | Keep where | Promote? |
|---|---|---|---|
| discard | One-off byproduct or low-value intermediate that is not needed after task completion. | Do not preserve beyond the immediate task result, or leave only inside task-local output if already created. | no |
| receipt | Evidence that a task ran, including scope, files, tools, result path, non-actions, and errors. | Sandbox output / receipt lane / recovery review bundle. | no |
| residue | Meaningful trace that may matter later but is not reusable or named yet. | Recovery bundle or selected residue folder only after Codex filtering. | no |
| candidate | Reusable judgment, threshold, pattern, prompt, script idea, or operating behavior worth review. | Candidate review packet; may be sent to Gemini for maturation. | no, proposal only |
| component | Named reusable function/part for a bounded lane, such as a runner pattern, receipt contract, or script harness. | Component candidate packet or bounded workbench design folder after Codex approval. | no, proposal only |
| space_update_proposal | Possible future update to current surface, baseline, guide, spec, registry, workflow, ontology, or memory, but not approved. | Explicit proposal packet for Codex/User/SOF review. | requires separate approval |
| STOP | Authority, memory, automation, cron, skill, config, baseline, policy, registry, workflow, ontology, current-position, output_manifest, or local authority mutation pressure. | Stop report / HOLD record only. | blocked |

## 9. Gemini Maturation Use

What Codex may batch-send to Gemini:
- Multiple filtered residues that repeat across Hermes runs.
- Candidate prompts/scripts/thresholds that need comparison.
- Component candidates that may need naming, grouping, or boundary refinement.
- Failure-mode clusters, WATCH patterns, and recurring handoff gaps.

What must not be sent:
- Secrets, auth, state.db, .env, sessions, credential logs, private raw logs, or unbounded repo dumps.
- Raw Hermes output flood without Codex filtering.
- Any packet framed as already-authoritative baseline, registry, workflow, ontology, memory, or current surface update.
- Anything requiring Gemini to make a promotion or authority decision.

What Gemini may propose:
- Names, labels, thresholds, clustering, comparison summaries, recurring failure patterns, candidate vessels, candidate component boundaries, and maturation hypotheses.

What Gemini cannot authorize:
- Baseline, memory, registry, workflow, ontology, schema, current-position, output_manifest, real cron, recurring automation, Hermes-main promotion, or VectorFL authority changes.

## 13. Failure Modes

List risks:
- output flood
  - Hermes may produce too many reports/receipts/artifacts; Codex must require summary receipts and classify aggressively.
- false memory
  - Repeated traces may feel remembered; they remain receipts/residue until selected and approved.
- repeated-run authority illusion
  - Many successful runs do not equal baseline, workflow, stable interface, or authority.
- Hermes skill/memory drift
  - Hermes should not save VectorFL standards into its own memory/skills unless a separate approval process exists.
- cron normalization
  - Manual-trigger dry-runs can become real recurring cron too quickly; real cron stays HOLD without explicit review.
- broad search drift
  - “Find missing assets” or “use the space” can become repo-wide search; explicit input packets must remain the default.
- Codex bottleneck
  - If every Hermes output needs deep review, Codex becomes overloaded; use discard/receipt/residue triage and batch Gemini maturation.
- Gemini over-ontology
  - Gemini may name patterns too fluently; names remain proposals until Codex/SOF/User approve.
