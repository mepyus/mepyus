AI 와 함께 25만 줄 규모의 프로젝트를 만들었습니다. 한 사람이, 6개월 만에! AI가 폭발적인 생산성을 제공한다는 건 이미 많은 분이 체감하고 계실 겁니다. 하지만 규모가 커지면 다른 문제가 보이기 시작합니다. AI는 확인하지 않고 추론에 의지하고, 작업이 길어지면 지침을 잊고, 규칙을 지키라고 해도 스스로 지켰다고 착각합니다. 이 글은 그 문제들을 하나씩 풀어가며 만들어낸 개발 파이프라인과, 그 파이프라인의 마지막 퍼즐이 된 AI 에이전트 관측 도구 Baden에 대한 이야기입니다.

Baden for Claude Code
0에서 25만 라인까지
Day1Company에서 Methii라는 서비스를 개발하고 있습니다. 업계에 오래 있었지만, AI 코딩 에이전트를 개발의 중심에 놓고 본격적으로 작업하기 시작한 건 작년부터입니다.

회사에서 신규 서비스를 만들 때, 모험적이면서도 멋진 제품을 만드는 건 생각보다 어렵습니다. 참여자의 능력이 부족해서가 아닙니다. 이해관계자가 많고 참여 인원이 늘어나면, 그 자체가 회사 입장에서 큰 투자가 됩니다. 투자 비용이 높을수록 실패할 수 없고, 한번 결정된 방향을 바꾸기 어려워집니다. 피봇 비용이 크기 때문입니다. 피봇한다고 성공을 담보할 근거도 없습니다. 결국 모범답안 같은 결과로 귀결되고, 심심한 서비스가 나옵니다. 오래 일하면서 그런 경험을 여러 번 했습니다. 그래서 이번에는 AI 코딩 에이전트를 근거로 단독 개발을 결정했습니다. 피봇 비용을 극적으로 낮추고, 스타트업의 가벼움을 조직 안에서 만들어보자는 판단이었습니다.

Methii는 그래프 기반 학습 캔버스 서비스입니다. 사용자가 어떤 주제에 대해 학습 트리를 만들면, AI가 콘텐츠를 생성하고, 캔버스 위에서 지식 구조를 시각화합니다. 여기에 퀴즈, 콘텐츠 스타일 변환, 다국어 지원, 실시간 협업 기능까지 들어갑니다. 서비스 하나를 만드는 게 아니라 하나의 플랫폼을 만드는 일이었고 개발은 현재도 계속 진행중입니다.

처음 2개월은 Anthropic의 Claude와 OpenAI의 Codex를 병행했습니다. 하나가 해결 못 하는 문제를 다른 에이전트가 풀어내는 경우가 꽤 있었고, 둘 다 해결 못 하는 건 결국 제가 직접 키보드를 잡았습니다. 이 시기는 AI 기반 개발의 가능성과 한계를 동시에 체감하는 탐색기였습니다.

이후에는 Claude와 단독으로 작업하며 규모를 키워갔습니다. 6개월이 지난 지금, Methii의 코드베이스는 이렇게 생겼습니다.

소스 파일 1,271개. 코드 약 249,000줄. Turborepo 모노레포 안에 14개의 앱과 9개의 공유 패키지가 들어 있습니다. React 프론트엔드에는 Konva.js 기반의 인터랙티브 캔버스가 있고, Express + Prisma로 구성된 API 서버에는 88개의 데이터베이스 모델과 158개의 API 라우트가 있습니다. Python LangChain FastAPI 서비스가 모든 LLM 상호작용을 처리하고, Temporal.io가 복잡한 워크플로를 오케스트레이션합니다. Next.js 기반의 백오피스, OpenCLIP 이미지-텍스트 유사도 서비스, 코드 실행 샌드박스까지. 여기에 자체 제작한 그래픽 엔진이 두 개 — Depix(선언적 다이어그램 DSL 엔진, 26,000줄)와 Fizzex(캔버스 기반 수식 편집기, 22,000줄)가 공유 패키지로 들어 있습니다. GCP Cloud Run, GKE, Cloud SQL 위에 Dockerfile 13개와 배포 스크립트 8개로 프로덕션 배포가 구성되어 있습니다.

Git 커밋 1,185개. 컨트리뷰터 1명.

설계와 판단은 제가 했고, 실행은 AI가 했습니다. 이 조합은 폭발적인 생산성을 만들어냈습니다. 한 사람이 이 규모의 시스템을 6개월 만에 만들 수 있었던 건 분명히 AI 덕분입니다. 그런데 규모가 커지면서 보이기 시작한 것들이 있었습니다.

AI는 읽었다고 착각한다
Methii의 LLM 파이프라인에는 Prompteer라는 자체 제작 프롬프트 관리 라이브러리가 있습니다. LLM 기반 서비스를 만들다 보면 프롬프트 관리가 금방 복잡해지는데, 오픈소스에 이를 위한 도구가 꽤 있었습니다. 하지만 대부분 프로젝트에 적용하기엔 불필요한 기능이 많았고, 저에게 필요한 건 훨씬 가벼운 것이었습니다. Next.js의 파일 기반 라우팅 개념을 프롬프트 관리에 차용하면 딱 적당히 가볍고 유용한 엔진을 만들 수 있겠다는 생각에 직접 만들었습니다. 101개의 마크다운 프롬프트 템플릿을 17개 도메인에 걸쳐 관리하며, {variable} 인터폴레이션, {#if} 조건문, {#for} 반복문, 그리고 Next.js 스타일의 [type] 동적 디렉토리 라우팅을 지원하는 독자적인 템플릿 엔진입니다.

문제는 Claude가 이 문법을 반복적으로 Handlebars와 혼동한다는 것이었습니다. Prompteer는 {variable}을 쓰지만 Handlebars는 {{variable}}을 씁니다. {#if}의 닫는 태그는 Prompteer에서 {/if}이지만, Handlebars에서는 {{/if}}입니다. AI의 학습 데이터에 표면적으로 유사한 Handlebars 패턴이 훨씬 많을 것이고 Prompteer는 존재하지 않으니, 명시적으로 "Prompteer 문법을 숙지하고 작업하라"고 지시해도 확률적으로 Handlebars 패턴으로 끌려가는 일이 반복됐습니다.

더 근본적인 문제는 따로 있었습니다. AI가 Prompteer의 문법 문서를 실제로 읽지 않고도, “읽은 것 같다”는 추론 위에서 작업을 진행한다는 것이었습니다. 파일을 열어 확인하는 도구를 갖고 있으면서도, 실제로 열지 않고 “이 파일은 아마 이런 내용일 것이다”라고 추론하여 프롬프트를 작성해놓습니다. 그리고 자신이 추론한 것과 실제로 읽은 것을 구분하지 못합니다.

이런 일은 프롬프트 시스템에서만 일어난 게 아니었습니다. Methii의 핵심 UX인 Knowledge Tree 그래픽 시스템은 Konva.js 위에 올린 19,000줄짜리 커스텀 렌더링 엔진입니다. 6개의 컨트롤러(Viewport, Drag, DropZone, Selection, StepDetach, Keyboard)가 사용자 인터랙션을 처리하고, 6종의 노드 렌더러가 각기 다른 시각적 표현을 가지고 있으며, 엣지 시스템은 베지어 곡선 경로 계산에 스프링 물리 기반의 흔들림(wobble) 효과까지 구현하고 있습니다. 이 시스템에서 무언가를 수정하려면, 수십 개 파일의 관계를 동시에 컨텍스트에 올려야 합니다. 한 파일만 읽어서는 동작을 예측할 수 없는 구조입니다.

AI는 엄청난 분량의 작업을 빠르게 처리합니다. 하지만 실제로 확인하지 않고 매우 많은 것을 “추론”에 의지합니다. 작은 프로젝트에서는 이 추론이 대부분 맞고, 틀려도 금방 잡을 수 있습니다. 하지만 25만 줄 규모에서, 14개 서비스가 얽히고, 독자적 문법과 자체 엔진이 존재하는 코드베이스에서는, 이 “확인 없는 추론”이 구조적 리스크가 됩니다.

문서는 특정 시점의 스냅샷일 뿐이다
처음에는 문서로 시스템을 설명했습니다. AI에게 코드베이스를 이해시키기 위해 상세한 설계 문서를 작성했습니다. 에디터 콘텐츠 아키텍처, 이벤트 시스템, i18n 아키텍처, 빌링 시스템, 콘텐츠 생성 워크플로, RAG 아키텍처, 지식 추천 시스템, 코드 실행 샌드박스 아키텍처, 파이프라인 모니터링… 프로젝트의 docs 디렉토리에는 57개의 마크다운 문서가 쌓였습니다.

문서는 효과가 있었습니다. AI가 시스템의 맥락을 파악하고 올바른 방향으로 구현하는 데 분명히 도움이 됐습니다. 하지만 코드는 매일 변합니다. 88개 모델의 관계가 바뀌고, API 엔드포인트가 추가되고, 컴포넌트가 리팩토링됩니다. 문서는 그 속도를 따라갈 수 없습니다.

문서와 코드의 불일치가 조금씩 쌓이기 시작했습니다. 처음에는 사소했습니다. 문서에는 ApiService라고 되어 있지만 코드에서는 이미 httpClient 싱글톤으로 전환된 상태. 문서에는 컨트롤러에 비즈니스 로직이 있다고 되어 있지만 서비스 레이어로 분리가 완료된 상태. 이런 불일치 하나하나는 작지만, AI가 오래된 문서를 참조해서 이미 리팩토링된 패턴으로 새 코드를 작성하기 시작하면 문제가 됩니다.

규모가 더 커지자 문서를 동기화하는 것 자체가 하나의 프로젝트가 되었습니다. 기능을 하나 추가하면 관련 문서 서너 개를 함께 업데이트해야 하고, 그 업데이트가 또 다른 문서와 충돌하지 않는지 확인해야 합니다. 문서를 유지하기 위해 소모하는 시간이 실제 개발 시간을 잠식하기 시작하는 지점이 왔습니다.

결국 하나의 결론에 도달했습니다.

시스템을 설명하는 것은 코드 그 자체여야 합니다. 문서는 특정 시점의 스냅샷일 뿐이고, 코드만이 항상 현재 상태를 정확하게 반영합니다. 그런데 코드가 시스템을 스스로 설명하려면, 코드 자체가 일관된 품질과 구조를 유지하고 있어야 합니다. 네이밍이 제멋대로이고, 패턴이 파일마다 다르고, 의존 방향이 뒤엉켜 있으면 코드를 읽어도 시스템이 보이지 않습니다.

그리고 품질을 유지하는 버팀목은 규칙입니다. 규칙도 코드와 함께 유지되어야 하는 대상입니다.

이 생각의 전환이, 이후 모든 것의 출발점이 됐습니다.

규칙에서 파이프라인으로
코드 품질을 지키는 규칙을 만들기로 했습니다. 그런데 어떤 규칙을 만들 것인가?

ESLint 같은 정적 분석 도구로 잡을 수 있는 것들 — unused imports, 세미콜론 스타일, 들여쓰기 — 은 이미 자동화되어 있습니다. 이런 것들을 규칙에 넣을 필요는 없습니다. 관심을 둔 것은 정적 분석이 잡을 수 없는 것들이었습니다.

“컨트롤러에서 50줄 이상의 복잡한 비즈니스 로직을 직접 작성하지 않는다.” “다른 도메인과의 상호작용을 정확히 이해한다.” “핵심 작업은 에러가 전파되어야 한다.” “레이아웃 계산을 렌더링 사이클 내에서 수행하지 않는다.” — 이런 규칙은 AST 파싱으로 검증할 수 없습니다. 코드의 의미와 맥락을 이해해야만 판단할 수 있습니다. 바로 LLM이 할 수 있는 일입니다.

240개의 MUST/MUST NOT 항목을 3계층으로 정리했습니다. 첫 번째 계층은 principles — 단일 책임, 의존 방향 준수, 공유 인스턴스 재사용, 중앙 관리, 최소 범위 갱신, 타입 안전성. 이 6개 원칙은 어떤 파일을 건드리든 항상 적용됩니다. 두 번째는 concerns(C1~C9) — 파일 구조, 싱글톤 패턴, 에러 처리, 하드코딩 금지 같은 교차 관심사 9개. 세 번째는 specifics(S-*) — Konva 렌더링 엔진, Zustand 스토어, React Query, Temporal 워크플로, LangChain 파이프라인 등 16개 도메인별 전용 규칙입니다.

rules/concerns/registry-pattern.md
규칙을 만들었습니다. 그런데 규칙은 만드는 것보다 지켜지게 하는 것이 어렵습니다.

작업 에이전트에게 “규칙을 확인하고 준수하라”고 지시할 수는 있습니다. 하지만 이건 자기 코드를 자기가 심판하는 구조입니다. 앞서 보았듯이 AI는 확인하지 않고도 “확인했다고 착각”할 수 있습니다. 규칙을 실제로 읽지 않고도 “이 규칙은 아마 이런 내용일 것이다”라고 추론하여 통과시켜버릴 수 있습니다.

그래서 Rule Guard라는 독립 에이전트를 만들어 규칙 검증을 전담시켰습니다. Claude Code의 커스텀 에이전트 기능을 활용한 서브에이전트로, 핵심 원칙은 세 가지입니다. 코드를 수정하지 않는다. 순수한 검증자 역할만 합니다. 규칙 파일을 반드시 읽고 판정한다. 추론이 아니라 실제 파일을 열어 MUST/MUST NOT 항목을 대조합니다. Bash는 보고와 grep 검색에만 사용한다. 에이전트의 권한을 극도로 제한하여 역할 이탈을 방지합니다.

작업 흐름은 이렇습니다. 작업 에이전트가 수정 계획을 세우면, Rule Guard를 호출하여 사전 검토를 받습니다. Rule Guard는 INDEX.yaml에서 해당 파일에 적용되는 규칙을 확인하고, 규칙 파일을 실제로 읽은 뒤, 수정 계획이 MUST/MUST NOT을 위반하는지 검증합니다. PASS면 수정을 진행하고, ISSUE면 계획을 수정해서 다시 검토를 받습니다. 수정이 완료되면 다시 Rule Guard를 호출하여 사후 검증을 받습니다. 실제 코드가 규칙을 준수하는지, grep으로 위반 패턴이 잔존하지 않는지 전수 확인합니다.

그런데 여기서 한 가지 문제를 더 풀어야 했습니다. 검증 결과가 구조화되지 않으면, 어떤 규칙이 자주 위반되는지, 어떤 도메인이 취약한지, 시간이 지나면서 품질이 나아지고 있는지 파악할 수 없습니다. Rule Guard의 검증 행위 자체를 정량화 가능한 데이터로 만들어야 했습니다.

그래서 프로토콜을 설계했습니다. ruleId 필수, 규칙별 개별 보고. 하나의 검증 보고에는 하나의 규칙 ID만 포함합니다. check_rule → rule_pass 또는 rule_violation → review_pass 또는 review_issue라는 일관된 보고 흐름. 위반 시에는 severity(critical, high, medium, low)를 명시하고, MUST/MUST NOT 원문을 인용한 구체적 판정 근거를 포함합니다.

Claude Code에서 작업이 길어지면 컨텍스트 압축(context compaction)이 일어납니다. 대화가 일정 길이를 넘으면 이전 맥락이 요약되면서 세부 정보가 소실됩니다. 이때 CLAUDE.md에 명시한 지침도, Rule Guard 호출 의무도, 보고 프로토콜도 함께 희석됩니다. 에이전트는 규칙 검증을 건너뛰기 시작하고, Rule Guard를 호출하지 않고 바로 수정에 들어가고, 보고 없이 파일을 읽고 쓰기 시작합니다.

지침이 프롬프트 수준에만 존재하는 한, 이 문제는 구조적으로 해결할 수 없습니다. AI의 기억은 본질적으로 불안정하고, 그 위에 세운 모든 약속은 시간이 지나면 흔들립니다.

이 문제에 대해 여러 방면에서 접근했습니다.

에이전트가 지금 규칙을 실제로 참조하고 있는지, Rule Guard를 호출했는지, 파일을 탐색은 했는지, 검증은 거쳤는지 — 이것들을 실시간으로 볼 수 있어야 파이프라인이 완성됩니다. 관측할 수 없으면 통제할 수 없습니다. 터미널에 흘러가는 텍스트 로그만으로는 에이전트의 행동 패턴을 파악할 수 없습니다.

설계 철학: 자유 서술, 사후 분류
Baden의 가장 핵심적인 설계 결정은 에이전트에게 고정된 이벤트 타입을 강요하지 않는다는 것입니다.

에이전트가 행동을 보고할 때, read_auth_logic, modify_handler, plan_refactor_approach, check_c5_compliance 같은 snake_case 키워드를 자유롭게 만들어 씁니다. 서버가 첫 단어를 기반으로 자동 분류합니다. read_로 시작하면 탐색(exploration), modify_나 create_면 구현(implementation), plan_이면 계획(planning), test_나 build_면 검증(rule_compliance)으로 분류됩니다. run_은 스킵 워드로 처리되어 run_test는 test로 분류됩니다.

이 접근법은 AI의 특성을 정면으로 반영합니다. AI 에이전트는 미리 정해진 분류 체계를 외우고 매번 정확하게 맞추는 일에 강하지 않습니다. 앞서 본 것처럼, 명시적 지침이 있어도 학습 데이터의 관성에 끌려가거나, 확인 없이 추론으로 처리하는 경향이 있습니다. 대신 자연어에 가까운 자유로운 서술에는 강합니다. Baden은 이 특성을 거스르지 않고 활용합니다. 에이전트는 부담 없이 보고하고, 시스템이 사후에 정리합니다.

여기에 2단계 액션 레지스트리 시스템이 더해집니다. 첫 번째 레이어는 접두사(prefix) 기반 광역 분류입니다. read_*, search_*, scan_*은 탐색, create_*, modify_*, fix_*는 구현으로 잡습니다. 두 번째 레이어는 상세 키워드 매칭으로 세부 카테고리를 덮어씁니다. 예를 들어 액션에 test라는 단어가 포함되어 있으면, 접두사가 무엇이든 검증 카테고리로 오버라이드됩니다. 시스템이 새로운 액션 패턴을 발견하면 대시보드에서 확인하고 태그를 붙일 수 있어, 사용할수록 분류 정확도가 높아지는 학습 구조입니다.

CLAUDE.md
MCP 도구: 에이전트와의 접점
Baden은 MCP(Model Context Protocol)를 통해 에이전트와 연결됩니다. 6개의 도구를 제공합니다.

baden_start_task: 사용자가 새로운 지시를 내리면 가장 먼저 호출합니다. 프로젝트 이름과 사용자의 지시 내용을 받아 taskId를 반환합니다. 이후 같은 작업의 모든 보고에 이 taskId가 포함되어, 하나의 지시에서 파생된 모든 행동이 하나의 체인으로 연결됩니다
baden_plan: 코드를 읽거나 수정하지 않더라도, 접근 방식을 결정하거나 계획을 세울 때 호출합니다. 계획 수립은 도구 호출이 아닌 “사고 과정”이기 때문에 별도로 보고하지 않으면 타임라인에서 보이지 않습니다. 이 도구가 있어야 에이전트가 계획 없이 바로 구현에 뛰어드는 패턴을 식별할 수 있습니다.
baden_action: 파일 읽기, 코드 수정, 검색 등 모든 행동을 실행하기 전에 호출합니다. 행동을 설명하는 snake_case 키워드, 대상 파일, 이유를 포함합니다.
baden_verify: 테스트, 빌드, 린트 등 검증 행동 후 결과를 보고합니다. “PASS 12/12” 같은 결과값이 포함됩니다.
baden_rule: 규칙 관련 활동을 보고합니다. 규칙 참조, 위반 발견, 수정 적용. ruleId와 severity를 포함합니다. Rule Guard 에이전트가 /tmp/baden-methii 래퍼를 통해 보내는 보고가 여기로 들어옵니다.
baden_complete_task: 작업이 완료되면 요약과 함께 호출합니다.
이 6개 도구가 “보고 → 확인 → 실행”이라는 원칙의 기술적 구현입니다. 에이전트는 모든 행동을 실행하기 전에 Baden에 보고합니다. 보고 없이 행동하지 않습니다.

타임라인: 에이전트의 작업 패턴을 공간으로 펼치다
Baden 대시보드의 중심은 타임라인 뷰입니다. 가로축은 시간, 세로축은 행동의 성격에 따라 다섯 개 레인으로 나뉩니다.

User: 사용자가 에이전트에게 내린 지시와 메인 에이전트가 작업 에이전트에게 내린 지시. 모든 작업 체인의 시작점입니다.
Exploration: 파일 읽기, 코드 검색, 의존성 확인, 문서 참조. 에이전트가 코드베이스를 탐색하는 행위가 여기에 표시됩니다.
Planning: 요구사항 분석, 접근 방식 결정, 작업 계획 수립. 코드를 건드리지 않는 사고 과정이 시각화됩니다.
Implementation: 코드 작성, 수정, 리팩토링, 파일 생성. 실제 변경이 일어나는 레인입니다.
Rules: 테스트 실행, 빌드, 린트, 규칙 참조, 위반 발견, 수정 적용. Rule Guard의 검증 사이클이 여기에 표시됩니다.

이 구조가 드러내는 것은 단순한 이벤트의 나열이 아니라 에이전트의 작업 패턴 자체입니다. 좋은 에이전트 작업은 Exploration → Planning → Implementation → Rules의 흐름을 자연스럽게 따릅니다. 파일을 먼저 읽고, 계획을 세우고, 구현하고, 검증합니다. 반대로 Exploration 레인이 비어 있는데 Implementation에 이벤트가 가득하다면, 에이전트가 코드를 확인하지 않고 추론에 의지하여 구현에 뛰어든 것입니다. 앞서 말한 “읽었다고 착각하는” 바로 그 패턴이 타임라인에서 즉시 식별됩니다.

하나의 사용자 지시에서 시작된 모든 행동은 taskId로 연결됩니다. 타임라인에서는 이 연결이 L자형 연결선으로 시각화되어, 복잡한 작업에서도 인과 관계의 흐름을 놓치지 않습니다. 메인 에이전트가 Rule Guard 서브에이전트를 호출하면, Rule Guard의 보고도 같은 taskId를 사용하므로 동일한 체인에 표시됩니다.

3분 이상의 유휴 구간은 자동으로 압축됩니다. 에이전트가 잠시 멈추거나 사용자가 결과를 검토하는 시간은 접혀서, 실제 작업이 일어난 구간에 집중할 수 있습니다. 하단의 미니맵은 전체 세션의 조감도를 보여주면서도 특정 구간으로 빠르게 이동할 수 있게 합니다. 줌과 패닝, 3단계 확장 토글(축소/확장/상세)로 원하는 수준의 디테일을 선택할 수 있습니다.

규칙 검증의 시각화
Rules 레인에서는 Rule Guard의 검증 사이클이 실시간으로 표시됩니다. 대시보드 상단의 카운터 — Check 58, Violation 7, Pass 69 — 가 현재 세션의 규칙 준수 상태를 한눈에 보여줍니다. 개별 이벤트를 클릭하면 드로어에 상세 정보가 나타납니다.

예를 들어 rule_violation 이벤트를 클릭하면, 어떤 규칙(S-temporal)을 위반했는지, 어떤 파일(generate-goalmap-content.workflow.ts)의 어떤 항목("MUST NOT: Activity 호출 시 트레이스 정보 누락")이 위반되었는지, severity는 high인지가 표시됩니다. Verification Cycles 패널을 열면 Rule Guard가 수행한 검증 사이클의 전체 내역 — 어떤 규칙을 검사했고, Pass인지 Issue인지, 시간은 얼마나 걸렸는지 — 을 시간순으로 볼 수 있습니다.

이 시각화가 있어야 비로소 “규칙이 실제로 지켜지고 있는가”라는 질문에 답할 수 있습니다. 규칙은 문서에 존재하지만 준수 여부는 블랙박스였던 상태에서, 준수 여부가 관측 가능한 데이터가 되는 것입니다.

아키텍처
서버는 Express + SQLite + WebSocket. SQLite를 선택한 건 로컬 도구의 성격에 정확히 맞기 때문입니다. 별도의 데이터베이스 서버 없이 ~/.baden/baden.db 파일 하나로 운영되며, WebSocket을 통해 이벤트가 발생하는 즉시 대시보드에 반영됩니다.

클라이언트는 React + Vite + Tailwind CSS SPA입니다. 타임라인은 SVG 기반으로 렌더링되며, 줌/패닝/갭 압축 등의 인터랙션이 자체 구현되어 있습니다. 이벤트 드로어는 핀 고정과 리사이즈를 지원하여 타임라인을 탐색하면서 동시에 이벤트 상세를 살펴볼 수 있습니다.

MCP 서버는 @modelcontextprotocol/sdk 기반의 stdio 트랜스포트로, 에이전트 쪽의 실패가 모니터링 시스템에 영향을 주지 않도록 에러를 조용히 무시하는 설계를 채택했습니다. 모니터링 도구가 작업 도구의 안정성을 해쳐서는 안 됩니다.

CLI(node bin/baden.js start)로 데몬을 실행하면 포트 3800에서 대시보드, API, WebSocket이 모두 시작됩니다. 프로젝트 등록은 대시보드 UI 또는 API 호출로 할 수 있고, 모니터링 대상 프로젝트의 CLAUDE.md에 보고 지침을 추가하면 연동이 완료됩니다.

INDEX.yaml과의 연동
Baden은 프로젝트의 rules/INDEX.yaml을 파싱하여 규칙 메타데이터를 등록합니다. 규칙 파일의 마크다운 본문을 렌더링하여 대시보드에서 직접 열람할 수 있고, 각 규칙별 참조/위반/수정 빈도를 추적합니다. 규칙 ID로 이벤트를 필터링하면, 특정 규칙이 얼마나 자주 검증되고 있는지, 위반 추이가 개선되고 있는지를 시계열로 볼 수 있습니다.

파이프라인의 완성
Baden은 앞서 구축한 모든 장치의 최종 수렴점입니다. CLAUDE.md의 최소 지침 → Rule Guard의 사전/사후 검증 → Hooks의 기억 재주입 → curl 브릿지를 통한 서브에이전트 보고 → 그리고 이 모든 것이 실제로 작동하고 있는지를 실시간으로 보여주는 Baden 대시보드. 각각의 장치는 독립적으로도 의미가 있지만, Baden이라는 관측 레이어가 더해져야 비로소 하나의 파이프라인으로 완성됩니다.

나에게 딱 맞는 바퀴
결과부터 말씀드리면, 이 파이프라인은 효과가 있었습니다.

최근 2개월간 제가 직접 코드를 작성한 경우는 전무합니다. 설계하고, 판단하고, 지시하고, 결과를 검토하는 것이 저의 역할입니다. 실행은 전부 AI가 수행합니다. 그리고 룰 시스템이 도입된 이후 최근 3주간, 에이전트가 엉뚱한 방향으로 구현을 진행하는 케이스가 거의 발견되지 않고 있습니다.

물론 이 시스템이 완벽하지는 않습니다. CLAUDE.md 기반의 보고 강제는 결국 에이전트가 지침을 따르느냐에 의존하는 부분이 있고, Hooks로 보정하더라도 100%를 보장할 수는 없습니다. Rule Guard 역시 LLM 기반이므로 자체적인 판단 오류 가능성이 존재합니다. 현재는 단일 머신의 로컬 환경에 한정되어 있어, 팀 단위의 에이전트 운용에는 추가적인 발전이 필요합니다.

그리고 오해하지 말아야 할 것이 있습니다. Baden과 Rule Guard가 기존의 엔지니어링 도구를 대체하는 것은 아닙니다. ESLint는 여전히 돌아가야 하고, SonarQube의 모니터링 리포트는 꼼꼼히 들여다봐야 합니다. 주요 시스템에 걸려 있는 수천 개의 테스트 케이스는 25만 줄짜리 코드베이스가 변경 한 줄에 무너지지 않게 잡아주는 가장 기본적인 안전망입니다. 정적 분석, 코드 품질 모니터링, 자동화된 테스트 — 이것들은 소프트웨어 공학이 수십 년에 걸쳐 쌓아올린 검증된 기반이며, AI 시대라고 해서 그 가치가 줄어들지 않습니다. Baden이 다루는 영역은 이 기반 위에 있습니다. 기계적으로 검증 가능한 것은 기존 도구가 처리하고, LLM만이 판단할 수 있는 의미와 맥락의 영역을 Rule Guard와 Baden이 맡습니다. 층위가 다릅니다.

하지만 이 경험 전체를 관통하는 더 큰 이야기가 있습니다.

개발자의 세계에는 오래된 격언이 있습니다. “바퀴를 재발명하지 마라.” 그래서 우리는 늘 이미 있는 바퀴를 찾아 씁니다. 대부분의 경우 그게 맞습니다. 하지만 오래 일하다 보면 알게 됩니다 — 세상에 바퀴는 많지만, 나에게 딱 필요한 만큼의 바퀴가 없는 경우가 놀라울 정도로 많다는 것을. 기존 도구가 80%는 맞지만 나머지 20%가 안 맞아서 끝없이 워크어라운드를 쌓거나, 결국 포기하고 그 도구의 제약 안에서 타협하게 됩니다. “직접 만들면 되지”라는 생각은 늘 했지만, 만드는 데 드는 비용이 너무 컸습니다.

AI 시대에 이것이 근본적으로 달라졌습니다. “나에게 딱 맞는 최적의 바퀴”를 만드는 데 주저함이 없어졌습니다. 101개의 프롬프트 템플릿을 관리하는 데 딱 맞는 프롬프트 매니저가 필요했습니다 — Prompteer를 만들었습니다. 지식 트리를 캔버스에 그리는 데 딱 맞는 다이어그램 엔진이 필요했습니다 — Depix를 만들었습니다. 수식을 캔버스에서 편집하는 데 딱 맞는 도구가 필요했습니다 — Fizzex를 만들었습니다.

그리고 AI 에이전트의 행동을 관측하는 데 기존의 어떤 도구도 딱 맞지 않았습니다 — Baden을 만들었습니다.

이것이 가능했던 건 AI가 실행력을 제공하기 때문입니다. 제가 가진 건 오래 일하며 쌓인 설계 감각과, “이건 이렇게 되어야 한다”는 판단력입니다. AI가 가진 건 그 판단을 코드로 빠르게 실현하는 실행력입니다. 이 둘이 결합하면 “딱 맞는 바퀴”를 만드는 비용이 극적으로 낮아집니다.

Baden 자체가 그 증거입니다. AI 에이전트 모니터링 도구라는 카테고리의 기존 제품을 찾아 쓰는 대신, 저의 개발 파이프라인에 정확히 맞는 도구를 직접 만들었습니다. 자유 서술 → 사후 분류라는 설계는 제가 에이전트를 운용하면서 관찰한 AI의 특성에서 나왔습니다. 5개 레인 구조는 제가 코드 리뷰할 때 실제로 확인하는 관점에서 나왔습니다. Rule Guard와의 연동 프로토콜은 제 프로젝트의 규칙 체계에 맞춰져 있습니다. 이건 범용 도구에서는 기대할 수 없는 핏(fit)입니다.

AI 에이전트의 능력은 계속 발전할 것입니다. 컨텍스트 윈도우는 더 커질 것이고, 추론 능력은 더 정확해질 것이고, 기억 소실 문제도 점차 개선될 것입니다. 하지만 발전하면 할수록, 아니 발전하면 할수록 — “에이전트가 제대로 하고 있는지 어떻게 알 것인가”라는 질문은 더 중요해질 것입니다. 더 많은 자율성을 주면 줄수록, 더 정밀한 관측이 필요합니다. 이것은 역설이 아니라 필연입니다.

6개월 전에는 AI와 함께 이 규모의 프로젝트를 만들 수 있을 거라고 장담하진 못했습니다. 그러나 지금은 더 좋은 모험을 할 수 있게 되었다는 것이 분명합니다. 그리고 그 모험을 계속하기 위해 필요한 것은 더 똑똑한 AI가 아니라, AI와 함께 일하는 더 나은 방법을 만들어가는 것입니다.

Baden은 그 과정에서 만들어진 하나의 답입니다.
