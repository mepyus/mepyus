# WashTank Engine And Data

## 목적

이 문서는 `WashTank`를 화면 모음이 아니라
작업 상태 전이 시스템으로 읽기 위한 문서다.

즉 이 문서의 관심사는

- 어떤 화면이 있는가

보다

- 탱크 상태를 어떻게 움직이려 했는가
- 데이터 구조를 어떻게 나누려 했는가
- 왜 `JMS` 같은 서비스 레이어가 필요했는가

에 있다.

## 기본 관점

`WashTank`를 읽다 보면 반복해서 드러나는 생각이 있다.

그것은:

1. 탱크는 단순 목록 항목이 아니다
2. 탱크는 작업 흐름을 통과하는 중심 객체다
3. 작업 흐름은 상태 전이와 이벤트로 다뤄야 한다
4. 프론트는 상태를 직접 바꾸기보다 그 전이를 요청해야 한다

즉 이 프로그램은 CRUD 앱보다
`상태 전이 엔진을 소비하는 현장 콘솔`
쪽에 더 가깝다.

## 핵심 서비스 레이어

관련 파일:

- `src/services/jms.js`
- `src/services/jms_core.js`
- `src/services/supabase.js`
- `src/supabaseClient.js`

여기서 읽히는 핵심은:

- 조회와 작업을 모두 서비스 레이어를 통해 묶는다
- 화면은 직접 DB를 만지지 않는다
- 상태 전이는 RPC 또는 통합 함수 호출을 통해 처리한다

즉 `JMS`는 단순 API 유틸이 아니라,
프론트가 현장 작업을 이벤트처럼 보내기 위한 통로 역할을 한다.

## JMS에서 보이는 엔진 사고

`jms.js`와 `jms_core.js`를 같이 보면
다음과 같은 사고가 읽힌다.

### 1. 작업(Job) 중심 사고

탱크는 그냥 존재하는 객체가 아니라,
`INBOUND`, `WASH`, `INSPECT`, `REPAIR`, `OUTBOUND`
같은 작업 타입을 가진다.

즉 현재 상태를 볼 때도
"탱크 자체"만 보는 것이 아니라
"탱크에 연결된 job_type / job_status"를 같이 본다.

### 2. 상태 전이 중심 사고

중요한 액션은 대부분:

- START
- COMPLETE
- CANCEL
- CREATE

같은 이벤트로 정리된다.

즉 화면이 직접 여러 필드를 제각각 수정하기보다,
하나의 작업 이벤트를 보내는 구조를 지향한다.

### 3. 위치 이동도 이벤트처럼 다룸

탱크는 작업 상태만 바뀌는 것이 아니라,
실제 위치 이동도 함께 다뤄진다.

즉 이 프로그램은 논리 상태와 물리 위치를 분리해서 보되,
둘 사이를 이벤트로 연결하려고 한다.

### 4. 프론트는 소비자이자 트리거

프론트 화면은:

- 현재 작업 상태를 읽고
- 특정 액션을 누르고
- 그 결과를 다시 조회한다

라는 구조를 반복한다.

즉 프론트는 작업 상태를 "보는 화면"이면서 동시에
"상태 전이 요청자"다.

## 데이터 구조 구상

관련 자료:

- `src/db.md`
- `src/tms.md`

이 문서들에서 읽히는 기본 구조는 아래와 같다.

### 1. tanks

탱크의 기본 마스터 정보다.

예:

- tank_number
- tank_type
- capa
- tare
- 각종 밸브 / 부속 정보

즉 탱크가 무엇인지에 대한 기본 원장이다.

### 2. tank_status

탱크의 현재 운영 상태를 담는 층이다.

예:

- cargo
- inbound_date
- scheduled_date
- current_client
- notice_priority
- location_id
- last_event_type

즉 마스터 정보와 별개로,
운영 중 계속 변하는 상태를 담으려는 층이다.

### 3. jobs

탱크에 부착된 실제 작업 단위다.

예:

- job_type
- status
- location_id
- started_at
- worker_id
- metadata

즉 탱크 위에 "어떤 공정 작업이 걸려 있는가"를 보는 층이다.

### 4. tank_event

행위 이력을 남기는 층이다.

예:

- event_type
- actor_id
- description
- category
- created_at

즉 현재 상태만이 아니라,
무슨 일이 있었는지의 연쇄를 남기려는 층이다.

### 5. locations

물리적 위치 구조를 담는 층이다.

예:

- yard_type
- block_name
- 최대 row / col
- 임시 여부

즉 탱크는 단순 상태값만이 아니라,
실제 야드 공간 위에 놓이는 객체라는 전제가 있다.

### 6. state_transition_rule

상태 전이 규칙을 별도로 두려는 층이다.

예:

- current_status
- event_type
- next_status
- priority
- condition_key

이건 매우 중요하다.

왜냐하면 이 구조는
"상태 전이를 코드 곳곳에 흩뿌리는 것"이 아니라
"전이 규칙을 테이블화하려는 생각"을 보여주기 때문이다.

## 이 구조가 의미하는 것

이 데이터 구조를 함께 보면,
`WashTank`는 단순히 화면이 많아진 프로젝트가 아니라
다음 다섯 축을 분리하려 한 프로젝트로 읽힌다.

1. 탱크 기본 정보
2. 현재 운영 상태
3. 공정 작업 단위
4. 이벤트 이력
5. 물리 위치

즉 "탱크 하나"를 여러 층으로 나눠서 보려는 시도다.

## 상태 전이 규칙에 대한 생각

`tms.md` 쪽에는 CLI 기반 테스트 코드와
승인 / 이동 / 입고 같은 절차 메모가 함께 들어 있다.

여기서 읽히는 중요한 생각은:

- 물리 이동과 논리 상태 전이는 함께 고려되어야 한다
- 각 함수는 테이블 관계 사슬을 무너뜨리면 안 된다
- 프론트 전에 CLI로 무결성을 검증하려 했다
- 승인도 단순 버튼이 아니라 상태 전이 이벤트다

즉 이 프로그램은 화면보다 먼저
`탱크 상태 전이 질서`를 만들려는 성격이 강하다.

## 화면과 엔진의 관계

이 문서에서 중요한 결론은 이거다.

화면은 각기 다른 공정을 담당하지만,
그 밑에서는 같은 엔진 사고를 공유한다.

예를 들면:

- `Inspection.jsx`는 측정 / 검사 이벤트를 보낸다
- `RepairShop.jsx`는 수리 관련 작업 상태를 다룬다
- `Delivery.jsx`는 출고 READY 작업을 소비한다
- `Officeout.jsx`는 DONE 작업에서 다음 공정을 만든다

겉보기에 화면은 다르지만,
실제로는 모두 탱크 + 작업 + 상태 전이 모델을 소비한다.

## 이 문서가 중요한 이유

`WashTank`를 나중에 다시 읽을 때
UI만 보면 "화면이 왜 이렇게 많은가"가 먼저 보일 수 있다.

하지만 엔진과 데이터 구조를 보면
오히려 반대로 읽힌다.

즉 화면이 많은 이유는
엔진 구조가 복잡해서가 아니라,
하나의 엔진 구조를 여러 운영 역할이 나눠 소비하기 때문이다.

이 문서는 바로 그 관점을 고정하기 위해 필요하다.

## 한 줄 정리

`WashTank`의 핵심은
여러 개의 JSX 화면이 아니라,
탱크를 작업과 상태 전이, 이벤트, 위치로 분리해서 다루려는
운영 엔진 사고에 있다.
