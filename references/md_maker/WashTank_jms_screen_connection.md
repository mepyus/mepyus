# WashTank JMS Screen Connection

## 목적

이 문서는 `WashTank` 안의 화면들이
`JMS` 서비스 레이어와 어떤 관계로 묶여 있는지를 정리하기 위한 문서다.

즉 이 문서의 관심사는

- 어떤 화면이 예쁜가

보다

- 각 화면이 무엇을 조회하는가
- 어떤 이벤트를 발생시키는가
- 왜 화면이 직접 DB를 만지지 않으려 했는가

를 정리하는 데 있다.

## 기본 원칙

`WashTank`에서 반복해서 보이는 중요한 원칙은 이거다.

- 화면은 직접 DB를 조작하지 않는다
- 데이터 통신은 서비스 레이어를 거친다
- 상태 전이는 이벤트 또는 RPC 호출을 통해 처리한다
- 작업 화면은 상태 소비자이자 이벤트 트리거다

즉 프론트는 데이터 원장이 아니라,
현장 작업과 사무 전환을 `JMS`에 요청하는 콘솔로 보는 편이 맞다.

## 중심 파일

관련 파일:

- `src/services/jms.js`
- `src/services/jms_core.js`
- `src/services/supabase.js`
- `src/supabaseClient.js`
- `src/main.jsx`

여기서 `main.jsx`는 여러 화면을 묶는 상위 조정자이고,
`jms.js`, `jms_core.js`는 화면 바깥에서 상태를 움직이는 서비스 계층이다.

## main.jsx 의 역할

`main.jsx`는 화면 라우팅만 하는 파일이라기보다,
실질적으로 상위 orchestration 레이어에 가깝다.

여기서 보이는 역할은:

- 여러 job type의 목록 조회
- 세척 베이 상태나 위치 데이터 보관
- 검사 큐 정규화
- 화면별로 필요한 데이터 shape를 맞춤
- 하위 화면에 `triggerAction`, `refresh` 계열 함수를 내려줌

즉 `main.jsx`는 모든 화면이 제멋대로 데이터를 가져가는 구조가 아니라,
상위에서 공통 데이터를 모아 내려주는 허브 역할을 한다.

## JMS 의 역할

`jms.js`는 단순 API wrapper가 아니다.

여기서는 크게 두 부류가 보인다.

### 1. Observation Layer

예:

- `getJobsByType`
- `getJobsByStatusAndTypes`
- `getDoneTransitionQueue`
- `getOfficeJobs`
- 기타 큐/목록 조회 함수

이 층의 역할은 현재 작업 상태를 읽는 것이다.

즉 화면은 먼저 여기서
"지금 어떤 탱크가 어떤 job 상태로 있는가"
를 읽는다.

### 2. Action / Transition Layer

예:

- job 생성
- 작업 시작
- 작업 완료
- 작업 취소
- 출고 요청 / 스케줄 / 완료
- 위치 이동 관련 RPC

이 층의 역할은 상태를 움직이는 것이다.

즉 화면은 이 층을 통해
"어떤 작업을 시작해 달라"
"다음 공정을 생성해 달라"
"이동을 반영해 달라"
를 요청한다.

## jms_core.js 의 의미

`jms_core.js`는 더 노골적으로
"작업 상태 전이 엔진의 클라이언트 인터페이스"처럼 보인다.

예:

- `createJob`
- `startJob`
- `completeJob`
- `cancelJob`

이 함수들은 결국
하나의 통합 RPC 또는 전이 함수에 payload를 만들어 보내는 형태다.

즉 화면은 세세한 DB 변경을 모르고,
`action + job_type + results`
를 보내는 쪽으로 단순화된다.

이건 화면 수가 많아질수록 중요하다.

왜냐하면 각 화면이 제각각 DB를 만지기 시작하면
전체 공정 질서가 금방 흩어지기 때문이다.

## 화면별 연결 방식

### Officein.jsx

이 화면은 사무실 기록 허브이므로,
주로 조회 성격의 `JMS` 함수를 더 많이 소비한다.

예상되는 연결:

- 완료 이력 조회
- 날짜 범위 기준 조회
- 특정 작업 결과 읽기

즉 `Officein`은 전환보다 기록 조회 쪽 비중이 크다.

### Officeout.jsx

이 화면은 전환 허브이므로,
조회와 전이 둘 다 강하게 연결된다.

예상되는 연결:

- DONE 상태 작업 조회
- 다음 job option 계산
- 출고 요청 생성
- 다음 공정 생성 또는 취소

즉 `Officeout`은 `JMS`를 가장 강하게 소비하는 사무실 화면 중 하나다.

### Eir.jsx

입고 화면은 시작점이기 때문에
새 작업 생성과 초기 입력 연결이 중요하다.

예상되는 연결:

- 입고 작업 생성
- 초기 상태 입력
- 이후 공정으로 넘길 준비

즉 `Eir`은 시작 이벤트를 트리거하는 성격이 강하다.

### WashingWaiting.jsx

세척 대기/진행 화면은
상태 조회와 `START/COMPLETE` 전이가 핵심이다.

예상되는 연결:

- WASH READY / IN_PROGRESS 조회
- 세척 시작
- 세척 완료

즉 큐 소비 + 상태 전이의 전형적인 화면이다.

### Inspection.jsx

검사 화면은 가장 단계적으로 `JMS`를 소비하는 화면 중 하나다.

예상되는 연결:

- 측정 시작 이벤트
- 측정값 기록 이벤트
- 검사 시작 이벤트
- 검사 완료 이벤트

즉 한 화면에서 여러 이벤트를 시간 순서대로 보내는 구조다.

### RepairShop.jsx

수리 화면은 예외 공정 처리 허브이므로,
조회보다 생성/전환 성격이 강하다.

예상되는 연결:

- 수리 등록
- 수리장 처리 요청
- 수리 완료
- 후속 공정 연결

즉 `RepairShop`은 단순 상태 소비자보다
새 작업을 강하게 만들어내는 화면에 가깝다.

### Delivery.jsx

출고 화면은 날짜 기반 READY 큐 소비자다.

예상되는 연결:

- 출고 READY 리스트 조회
- 특정 날짜 기준 조회
- 출고 준비 완료 처리

즉 `Delivery`는 조회와 단일 완료 이벤트 중심의 화면이다.

### Shuttle.jsx

셔틀 화면은 위치 이동 관련 이벤트를 분리해서 다루는 특수 화면이다.

예상되는 연결:

- 이동 대상 조회
- 이동 시작
- 이동 완료
- 승인 요청 연결

즉 일반 공정 job과 위치 이동 이벤트가 같이 만나는 화면이다.

### Ehandler.jsx / Fhandler.jsx

이 둘은 현장 역할 화면이기 때문에,
구체적으로 어떤 `JMS` 함수를 호출하는지는 파일마다 다르더라도
기본적으로는 현장 역할 단위 작업 소비자라고 보는 편이 맞다.

즉 공정 자체보다
작업자와 부지 역할 기준으로 `JMS`를 소비하는 콘솔이다.

## 왜 이 구조가 중요했는가

화면이 많아질수록 중요한 건
각 화면이 같은 엔진 질서를 공유하느냐이다.

`WashTank`는 바로 이 점에서
서비스 레이어를 강하게 의식한 흔적이 있다.

그 이유는 다음과 같다.

1. 같은 탱크가 여러 화면에 걸쳐 보인다
2. 같은 상태가 여러 공정을 지나면서 변한다
3. 화면이 직접 DB를 만지면 규칙이 분산된다
4. 상태 전이 규칙을 서비스 쪽에 묶어야 일관성이 생긴다

즉 `JMS`는 편의용 유틸이 아니라,
여러 화면을 하나의 공정 질서 아래 묶기 위한 장치다.

## 이 문서가 중요한 이유

`WashTank`를 다시 볼 때,
화면별로 따로따로 이해하면
"왜 화면이 이렇게 많아졌는지"만 남기 쉽다.

하지만 `JMS`와 연결해서 보면 오히려 반대로 읽힌다.

즉 화면이 많은 것이 문제가 아니라,
모든 화면이 하나의 상태 전이 엔진을 같이 보도록 만들려 했다는 점이 보인다.

이 문서는 바로 그 관점을 고정하기 위해 필요하다.

## 한 줄 정리

`WashTank`의 화면들은 각각 다른 공정을 담당하지만,
모두 `JMS`라는 서비스 레이어를 통해
탱크 + 작업 + 상태 전이 질서를 공유하도록 설계된 콘솔들이다.
