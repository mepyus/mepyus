# WashTank Process Flow

## 목적

이 문서는 `WashTank` 폴더 안에서 읽히는 공정 흐름을
작업 단계 기준으로 다시 정리하기 위한 문서다.

개별 JSX 파일을 하나씩 설명하기보다,
탱크가 어떤 단계들을 거치도록 상상되었는지를
공정 흐름 기준으로 묶어본다.

## 기본 흐름

`WashTank`에서 보이는 기본 흐름은 아래처럼 읽힌다.

1. 입고 접수
2. 입고 / EIR 확인
3. 세척 대기
4. 세척 진행
5. 검사
6. 수리 또는 후속 조치
7. 출고 준비
8. 출고
9. 부지 간 이동이 필요한 경우 셔틀 처리

이 흐름은 항상 직선으로만 가는 것이 아니라,
검사 이후 수리로 빠지거나,
수리 후 다시 세척이나 검사로 돌아가는 식의 분기도 염두에 둔 구조로 보인다.

## 1. 입고 단계

입고 단계는 탱크를 시스템 안으로 들이는 출발점이다.

여기서 중요한 것은 단순 등록이 아니라,

- 어떤 탱크인가
- 현재 어떤 상태인가
- 입고 시 어떤 정보가 붙는가
- 이후 세척으로 갈지 보관으로 갈지

를 결정하는 기준을 만드는 것이다.

관련 화면:

- `Eir.jsx`
- `Officein.jsx`

관련 메모:

- `db.md`
- `tms.md`

## 2. 입고 / EIR 확인

입고 직후에는 EIR 성격의 확인 단계가 들어간다.

이 단계는 탱크 정보를 받고,
기초 상태를 확인하고,
이후 공정으로 넘기기 위한 초기 판정을 붙이는 역할에 가깝다.

이 화면은 단순 조회가 아니라,
탱크를 본격 공정으로 넘기기 위한 관문처럼 읽힌다.

관련 화면:

- `Eir.jsx`

## 3. 세척 대기

세척은 바로 실행되기보다
대기 큐와 실행 큐가 나뉘는 방향으로 설계된 흔적이 보인다.

즉 중요한 것은 "세척 화면" 하나가 아니라,

- 세척 대상이 누구인가
- 현재 대기인지
- 이미 진행 중인지
- 어느 베이나 슬롯에 올라가 있는지

를 따로 보는 것이다.

관련 화면:

- `WashingWaiting.jsx`

## 4. 세척 진행

세척 진행 단계는 대기 상태를 실제 작업 상태로 바꾸는 단계다.

여기서 읽히는 핵심은:

- READY와 IN_PROGRESS 구분
- 베이/슬롯 점유 상태
- 실행 시작과 완료를 명시적 이벤트로 다루려는 방향

이다.

즉 세척은 단순 상태값이 아니라,
물리적 공간 점유와 작업 상태 전이가 같이 묶인 단계로 보인다.

관련 화면:

- `WashingWaiting.jsx`
- `head.jsx`

## 5. 검사

검사 단계는 `WashTank`에서 꽤 분명하게 설계된 부분이다.

특히 검사 화면은:

- 측정 시작
- 측정값 기록
- 검사 시작
- 검사 완료

를 분리해서 다룬다.

즉 검사는 한 번의 버튼 클릭이 아니라,
측정과 검사 행위를 나눠서 기록하려는 의도가 강하다.

관련 화면:

- `Inspection.jsx`

## 6. 수리

검사 이후 문제가 있거나 별도 조치가 필요하면 수리 단계로 이어진다.

수리 단계의 특징은:

- 수리 요청 생성
- 수리장 처리
- 완료 입력
- 부지에 따라 처리 방식이 달라질 수 있음

이다.

수리 화면은 단순 카드 보드보다
리스트 + 메인 작업 입력형 워크벤치에 더 가깝게 설계되어 있다.

관련 화면:

- `RepairShop.jsx`

## 7. 장비기사 작업

`WashTank`의 특징 중 하나는
장비기사 화면이 별도로 분리되어 있다는 점이다.

이건 단순 기능 분리보다
"누가 이 작업을 담당하는가"를 화면 구조에 반영하려던 흔적으로 읽힌다.

관련 화면:

- `Ehandler.jsx` : 1부지 장비기사 페이지
- `Fhandler.jsx` : 2부지 장비기사 페이지

즉 공정 단계뿐 아니라
부지와 역할도 시스템의 일부로 본 셈이다.

## 8. 셔틀 이동

탱크가 1부지와 2부지 사이를 이동해야 하는 경우,
별도의 셔틀 화면이 개입한다.

셔틀 단계는 단순 위치 변경이 아니라,

- 어느 부지에서 출발하는가
- 어디로 이동하는가
- 이동 준비 상태인가
- 실제 이동 중인가
- 이동 완료 후 승인 신호가 필요한가

를 명시적으로 다루려는 구조다.

관련 화면:

- `Shuttle.jsx`

## 9. 출고 준비 / 출고

출고는 바로 나가는 단계라기보다,
`READY` 큐와 날짜 축이 있는 준비 단계로 먼저 읽힌다.

즉 출고 단계의 관심사는:

- 언제 나가야 하는가
- 어떤 탱크가 준비되었는가
- 우선순위는 어떤가
- 현재 위치는 어디인가

같은 운영 요소다.

관련 화면:

- `Delivery.jsx`
- `Officeout.jsx`

## 10. 사무실 전환 허브

이 프로그램에서 중요한 역할 중 하나는
사무실이 DONE 작업을 다음 공정으로 전환하는 허브라는 점이다.

즉 현장은 작업을 끝내고,
사무실은 그 결과를 보고 다음 단계로 넘긴다.

이 전환 허브가 있기 때문에,
전체 프로그램은 단순 현장 앱이 아니라
승인과 전환이 섞인 운영 시스템이 된다.

관련 화면:

- `Officeout.jsx`

## 11. 사무실 기록 허브

반대로 `Officein` 쪽은
완료 이력과 기록 축적의 허브에 가깝다.

즉 이 프로그램은 "지금 무엇을 할까"만이 아니라,
"무엇이 끝났고 어떤 기록이 남았는가"도 같이 보려 했다.

관련 화면:

- `Officein.jsx`

## 12. 공정 흐름의 특징

이 공정 흐름을 읽을 때 중요한 특징은 아래와 같다.

1. 직선형 흐름이지만 분기가 존재한다.
2. 세척, 검사, 수리, 출고가 독립 화면으로 나뉜다.
3. 부지와 작업자 역할도 별도 화면으로 나뉜다.
4. 사무실은 단순 조회자가 아니라 전환 허브다.
5. 상태 전이는 이벤트와 서비스 레이어를 통해 통합하려 했다.

즉 `WashTank`는 단순 페이지 모음이 아니라,
탱크를 공정 흐름 속에서 움직이는 운영 콘솔 묶음으로 읽는 것이 맞다.

## 13. 이 문서를 보는 방법

이 문서는 최종 정답 흐름을 고정하려는 것이 아니라,
현재 파일들에서 읽히는 흐름의 초벌 정리다.

앞으로 더 읽으면서 아래를 덧붙일 수 있다.

- 실제 분기 조건
- 어떤 화면이 어느 시점에 추가되었는지
- 사무실과 현장 사이 역할 차이
- 부지 간 이동이 왜 별도 화면이 되었는지

즉 이 문서는 이후 더 자세한 `WashTank` 기록 문서를 만들기 위한
공정 중심 스캐폴드로 보는 편이 맞다.
