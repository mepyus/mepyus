# WashTank Overview

## 목적

이 문서는 `WashTank` 프로그램의 최종 사양서가 아니다.  
이 문서의 목적은 탱크 프로그램을 만들던 과정에서 어떤 공정 의도와 역할 분해가 있었는지 다시 읽을 수 있도록 기록하는 것이다.

즉 이 문서는 "무엇이 구현되었는가"보다 먼저,  
"왜 이런 화면들이 생겼는가"를 복원하기 위한 개요 문서다.

## 프로그램의 기본 방향

`WashTank`는 탱크 하나를 중심으로 입고, 세척, 검사, 수리, 출고, 셔틀 이동까지 이어지는 흐름을 운영하려는 프로그램이다.

이 프로그램은 단순 조회 화면 하나로 끝나는 구조가 아니라,

- 사무실 승인과 전환
- 현장 작업 입력
- 부지 간 이동
- 장비기사 역할 분리

를 각각 다른 화면으로 나누어 다루려는 방향을 가진다.

즉 핵심은 "탱크 상태를 본다"가 아니라  
"탱크를 공정 흐름 안에서 움직인다"에 더 가깝다.

## 전체 공정 흐름

이 폴더에서 읽히는 기본 흐름은 대체로 아래와 같다.

1. 입고
2. 세척 대기 / 세척 진행
3. 검사
4. 수리
5. 출고 준비 / 출고
6. 부지 간 셔틀 이동
7. 사무실 승인 및 다음 공정 전환
8. 1부지 / 2부지 장비기사 작업

즉 이 프로그램은 개별 기능 페이지의 모음이 아니라,  
탱크의 흐름을 단계별로 소비하는 콘솔 묶음으로 보는 편이 맞다.

## 화면 분해의 이유

처음부터 하나의 대시보드만으로 운영하려 했던 것이 아니라,
실제 작업이 들어가면서 공정별 입력과 판단이 달라졌기 때문에 화면이 분리된 것으로 보인다.

이 분해의 이유는 크게 세 가지로 읽힌다.

1. 공정마다 필요한 입력값이 다르다.  
   예를 들어 입고 기록, 검사 측정값, 수리 메모, 출고 준비 정보는 같은 화면에서 다루기 어렵다.

2. 현장 화면과 사무 처리 화면의 책임이 다르다.  
   현장은 실제 작업을 진행하고, 사무실은 승인과 다음 공정 전환을 다룬다.

3. 부지와 작업자 역할 차이를 반영할 필요가 있다.  
   1부지와 2부지의 장비기사 화면이 따로 있는 점이 이를 보여준다.

## 주요 화면과 역할

### 사무실 계열

- `Officein.jsx`
  완료 이력과 입고 기록을 확인하는 사무실 허브

- `Officeout.jsx`
  `DONE` 상태 작업을 다음 공정으로 넘기는 전환 허브

### 현장 계열

- `Eir.jsx`
  입고 / EIR 공정의 실제 작업 화면

- `WashingWaiting.jsx`
  세척 공정 대기 및 진행 상태를 보는 화면

- `Inspection.jsx`
  가스 측정과 검사 완료를 처리하는 검사 화면

- `RepairShop.jsx`
  수리 등록, 수리장 처리, 완료 입력 화면

- `Delivery.jsx`
  출고 `READY` 큐와 출고 준비 완료 처리를 다루는 화면

- `Shuttle.jsx`
  1부지와 2부지 사이 이동을 처리하는 화면

### 장비기사 계열

- `Ehandler.jsx`
  1부지 장비기사 페이지

- `Fhandler.jsx`
  2부지 장비기사 페이지

### 상위 래퍼 / 보드 계열

- `Workspace.jsx`
  상위 작업 공간 래퍼

- `head.jsx`
  비교적 초기형 공정 보드 / 모니터 성격의 화면

## 사무실 / 현장 / 장비기사 분리

이 폴더를 읽을 때 중요한 건 화면을 파일명 기준보다 역할 기준으로 나누는 것이다.

### 사무실

- `Officein.jsx`
- `Officeout.jsx`

### 현장

- `Eir.jsx`
- `WashingWaiting.jsx`
- `Inspection.jsx`
- `RepairShop.jsx`
- `Delivery.jsx`
- `Shuttle.jsx`

### 장비기사

- `Ehandler.jsx`
- `Fhandler.jsx`

이 구조는 프로그램이 단일 대시보드에서 출발했더라도,
결국 운영 단계에서는 역할별 콘솔로 쪼개지는 방향을 택했다는 점을 보여준다.

## 상태 전이 엔진에 대한 생각

`WashTank`의 중요한 특징은 화면이 직접 DB를 만지는 방향보다,
서비스 레이어를 통해 상태를 움직이려 했다는 점이다.

관련 파일은 다음과 같다.

- `services/jms.js`
- `services/jms_core.js`

여기서 읽히는 핵심 생각은 이렇다.

- 상태 전이는 이벤트로 처리한다
- 작업(Job) 생성과 상태 전환을 분리한다
- 위치 이동도 별도 함수 / RPC로 다룬다
- 프론트는 상태를 보여주고 이벤트를 발생시키는 콘솔이다

즉 이 프로그램은 단순 CRUD 화면보다는,
`JMS`라는 공정 엔진을 프론트에서 소비하는 구조를 지향한다.

## 데이터 구조 구상

`db.md`와 `tms.md`를 보면, 프로그램은 최소한 아래 구조를 전제로 한다.

- 탱크 기본 정보
- 현재 상태
- 작업(Job)
- 이벤트 로그
- 위치
- 상태 전이 규칙

관련 문서:

- `db.md`
- `tms.md`

이 점이 중요한 이유는,
화면이 많아 보여도 결국 전부 같은 데이터 흐름을 공유한다는 뜻이기 때문이다.

즉 핵심 객체는 화면이 아니라 탱크와 작업, 이벤트다.

## 구현 과정에서 보이는 흔적

이 폴더는 완전히 정돈된 완성 앱 소스라기보다,
공정 해석과 화면 실험이 누적된 아카이브에 가깝다.

그 흔적은 다음처럼 보인다.

- 실제 운영 콘솔처럼 보이는 화면이 있다
- 프로토타입 성격이 강한 화면도 있다
- 데이터 구조와 전이 규칙 메모가 코드 옆에 같이 남아 있다
- 일부 파일은 구조 실험용 중간 단계로 보인다

즉 이 폴더는 결과물만이 아니라,
"탱크 프로그램을 어떤 방식으로 생각했는가"를 같이 담고 있다.

## 이 기록이 중요한 이유

이 문서를 남기는 이유는 코드 설명 자체보다,
프로그램을 어떤 이유로 공정 단위, 역할 단위, 부지 단위로 나눴는지를 복원하기 위해서다.

나중에 이 폴더의 `md` 파일과 코드 파일을 함께 읽으면,

- 어떤 업무를 먼저 의식했는지
- 왜 화면이 이렇게 나뉘었는지
- 엔진과 화면을 어떤 관계로 보았는지

를 다시 추적할 수 있다.

즉 이 문서는 구현 설명서가 아니라,
`WashTank`를 만들던 사고의 입구를 남기는 문서다.

## 앞으로의 읽기 기준

이 폴더는 파일 단위로 읽기보다 아래 기준으로 읽는 편이 낫다.

1. 사무실 화면
2. 현장 화면
3. 장비기사 화면
4. 셔틀 / 출고 / 수리 같은 특수 공정 화면
5. `JMS` 서비스 레이어
6. `db.md`, `tms.md` 같은 데이터 / 상태 전이 메모

이렇게 읽어야 `WashTank`가 단순한 JSX 모음이 아니라,
탱크 공정을 운영하기 위한 단계별 콘솔 실험이었다는 점이 보인다.
