# WashTank Screen Creation Reasons

## 목적

이 문서는 `WashTank` 안의 주요 화면들이
왜 따로 만들어졌는지를 직접적으로 적기 위한 문서다.

지금 이 문서의 목적은
정확한 역사 연표를 확정하는 것이 아니라,
현재 파일 구조와 코드 흔적을 바탕으로
"이 화면이 왜 필요해졌는가"를 복원 가능한 문장으로 남기는 것이다.

즉 기능 설명보다
생성 이유를 남기는 데 더 가깝다.

## 기본 전제

`WashTank`는 처음부터 완벽히 분리된 제품 구조로 만들어진 것처럼 보이지 않는다.

오히려 다음 순서가 있었던 것으로 읽힌다.

1. 전체 공정을 한 번에 보고 싶은 감각이 먼저 있었다
2. 실제 작업을 넣으려 하자 공정별 입력이 달랐다
3. 그래서 화면이 단계별로 분리되기 시작했다
4. 이후 역할과 부지 차이까지 화면으로 나뉘었다

즉 화면들은 단순히 많아진 것이 아니라,
운영 감각이 세분화되면서 분화된 결과로 보는 편이 맞다.

## Officein.jsx 가 생긴 이유

이 화면은 "현장에서 지금 뭘 하나"보다
"끝난 작업을 사무실에서 어떻게 읽고 정리할 것인가"가 필요해서 생긴 것으로 보인다.

필요해진 이유:

- 완료 이력을 날짜 기준으로 보고 싶었기 때문
- 입고 이후 기록을 사무실에서 다시 확인할 허브가 필요했기 때문
- 현장 처리와 별개로 문서/기록 관점의 화면이 필요했기 때문

즉 `Officein`은 공정 시작 화면이 아니라,
공정의 결과를 사무실 관점에서 축적하는 화면으로 읽힌다.

## Officeout.jsx 가 생긴 이유

이 화면은 "작업이 끝났다" 이후가 문제였기 때문에 생긴 화면에 가깝다.

필요해진 이유:

- DONE 상태 작업을 그냥 끝으로 두기 어려웠기 때문
- 다음 공정을 누가 결정할지 정리할 필요가 있었기 때문
- 출고, 수리, 검사, 보관 같은 후속 분기가 필요했기 때문

즉 `Officeout`은 종료 화면이 아니라,
현장 종료 이후의 전환 허브를 만들기 위해 생긴 화면이다.

## Eir.jsx 가 생긴 이유

입고는 단순 등록이 아니라,
탱크를 시스템 안으로 들이는 첫 공식 단계였기 때문에
별도 화면이 필요했던 것으로 보인다.

필요해진 이유:

- 입고 시점의 탱크 정보를 따로 다뤄야 했기 때문
- 초기 검사 / 확인 성격의 입력이 필요했기 때문
- 이후 세척이나 보관으로 넘기기 전의 시작점이 필요했기 때문

즉 `Eir`은 입고를 하나의 독립 공정으로 다루기 위해 생긴 화면이다.

## WashingWaiting.jsx 가 생긴 이유

세척은 단순 시작/완료만으로 다루기 어려웠기 때문에
대기와 실행을 분리해서 볼 필요가 있었던 것으로 보인다.

필요해진 이유:

- 세척 대상이 누군지 큐처럼 보고 싶었기 때문
- READY와 IN_PROGRESS를 따로 보고 싶었기 때문
- 세척장 자원과 작업 순서를 동시에 봐야 했기 때문

즉 `WashingWaiting`은 세척을 작업 보드처럼 운영하기 위해 생긴 화면이다.

## Inspection.jsx 가 생긴 이유

검사는 한 번의 완료 버튼으로 끝내기 어려운 공정이었기 때문에
세부 단계가 있는 별도 화면이 필요했던 것으로 보인다.

필요해진 이유:

- 측정 시작과 측정 기록을 분리하고 싶었기 때문
- 검사 시작과 검사 완료도 따로 다루고 싶었기 때문
- 검사 인력과 역할을 명시적으로 남기고 싶었기 때문

즉 `Inspection`은 검사 행위를 더 세밀한 단계로 남기기 위해 생긴 화면이다.

## RepairShop.jsx 가 생긴 이유

수리는 보통 예외 처리에 가까운 공정이라
단순 상태 변경이 아니라 메인 작업 화면이 필요했던 것으로 읽힌다.

필요해진 이유:

- 수리 요청을 별도로 다뤄야 했기 때문
- 수리장 이동 여부를 판단해야 했기 때문
- 수리 메모와 완료 입력이 필요했기 때문
- 부지에 따라 처리 방식이 다를 수 있었기 때문

즉 `RepairShop`은 예외 공정을 별도 작업 허브로 만든 결과다.

## Delivery.jsx 가 생긴 이유

출고는 단순 마지막 단계가 아니라,
날짜와 우선순위, 준비 상태를 함께 보는 운영 큐였기 때문에
별도 화면이 필요했던 것으로 보인다.

필요해진 이유:

- 출고 예정일 기준으로 리스트를 보고 싶었기 때문
- 어떤 탱크가 준비되었는지 구분해야 했기 때문
- 현장 작업자가 READY 큐를 기준으로 움직여야 했기 때문

즉 `Delivery`는 출고를 일정 기반 운영 단계로 보기 위해 생긴 화면이다.

## Shuttle.jsx 가 생긴 이유

부지 간 이동은 단순 위치 변경으로 흡수되지 않았고,
별도 작업으로 다뤄야 할 만큼 중요했던 것으로 보인다.

필요해진 이유:

- 1부지와 2부지의 출발 방향이 달랐기 때문
- 이동 시작과 완료를 따로 관리해야 했기 때문
- 이동 완료 후 승인 연결이 필요했기 때문

즉 `Shuttle`은 위치 이동을 공정 이벤트로 승격시키기 위해 생긴 화면이다.

## Ehandler.jsx 와 Fhandler.jsx 가 생긴 이유

이 둘은 공정 화면만으로는 현장 운영을 다 담기 어렵다는 판단에서 나온 것으로 읽힌다.

필요해진 이유:

- 장비기사 역할이 별도 작업 단위였기 때문
- 1부지와 2부지의 현장 역할 차이가 있었기 때문
- 공정 단계보다 사람/부지 역할이 더 중요한 순간이 있었기 때문

즉 `Ehandler`와 `Fhandler`는
현장 작업자 역할을 직접 화면으로 분리하기 위해 생긴 페이지다.

## head.jsx 가 남아 있는 이유

이 화면은 세부 화면들보다 앞선 단계의 감각을 담고 있기 때문에,
지금도 흔적으로 중요하다.

남아 있는 이유:

- 공정 전체를 한 보드에서 보고 싶었던 초기 감각을 보여주기 때문
- WASH / INSPECT / OUTBOUND를 공통 패턴으로 다루려 했기 때문
- 이후 세부 화면으로 분화되기 전의 설계 흔적이기 때문

즉 `head.jsx`는 현재 주력 화면이라기보다,
분화 이전의 사고를 보여주는 기준점에 가깝다.

## Workspace.jsx 와 OfficePageContainer.jsx 가 필요한 이유

이 둘은 직접 작업을 수행하는 화면보다,
상위 컨테이너와 연결 계층이 필요했기 때문에 생긴 것으로 보인다.

필요해진 이유:

- 공통 메시지나 에러를 감싸는 레이어가 필요했기 때문
- 초기 데이터 로드와 검색을 본체 화면에서 떼고 싶었기 때문
- 상위 화면과 하위 화면을 연결하는 래퍼가 필요했기 때문

즉 이 파일들은 업무 화면보다는 연결 구조의 흔적이다.

## 한 줄 정리

`WashTank`의 화면들은 기능이 많아서 생긴 것이 아니라,
공정 / 전환 / 역할 / 부지 / 운영 큐를 따로 다뤄야 할 필요가 커지면서
하나씩 분화된 결과로 보는 편이 맞다.
