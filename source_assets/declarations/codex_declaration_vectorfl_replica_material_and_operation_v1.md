# codex_declaration_vectorfl_replica_material_and_operation_v1

## 1. 문서 목적
이 문서는 `vectorfl_replica` 를 단순 코드 저장소나 개별 스크립트 묶음으로 보지 않고,
**문서-입력-판독-실행-기록-정리**가 함께 순환하는 하나의 엔진 작업공간으로 선언하기 위한 상위 선언문이다.

이 선언문은 앞으로 Codex가 다음 사실을 흔들리지 않는 전제로 삼도록 만들기 위해 존재한다.

- `vectorfl_replica` 전체는 하나의 엔진 작업공간이다.
- 너와 사용자 사이에서 생성되는 구조화 문서는 단순 프롬프트가 아니라 엔진의 핵심 재료다.
- Codex 실행은 그 문서 재료에서 파생되는 운영 경로 중 하나다.
- 모든 실행은 가능한 한 작은 사실 기록으로 남아야 하며, status 문서는 그 기록을 나중에 정리한 압축층이어야 한다.
- 입력기는 좁게 잠그지 않되, 입력마다 같은 방식으로 처리하지 않는다.

## 2. 한 줄 선언
`vectorfl_replica` 는

**구조화 문서, 외부 자료, 실행 결과, 폴더와 스크립트 같은 구성요소를 함께 다루며,
입력 -> 분절/마킹 -> 판독 -> 실행 -> 기록 -> 정리 로 순환하는 repo-scale 엔진 작업공간**이다.

더 짧게 말하면:

**`vectorfl_replica` 는 문서 재료와 실행 사건이 함께 축적되는 운영 엔진이다.**

## 3. 최우선 해석
앞으로 Codex는 아래 해석을 최우선 기준으로 받아들인다.

### 3.1 저장소 전체 해석
`vectorfl_replica` 는 `app/` 만이 아니라 아래 전체를 포함한 엔진이다.

- `app/` = 엔진 본체
- `scripts/` = 엔진 조작면 / 실행 팔
- 루트 `runtime/` = 엔진 결과 표면
- `references/` = 엔진 교정 기억
- `*_status.md` = 엔진 자기 설명 계층
- ledger / event log / ticket 기록 = 엔진 운영 흔적 계층

즉 이 저장소는 코드만이 아니라
**운영과 기록까지 포함한 엔진**으로 읽어야 한다.

### 3.2 문서 재료 해석
너와 사용자 사이의 대화에서 생성되는 아래 문서들은
단순히 Codex에게 일을 시키기 위한 보조 텍스트가 아니다.

- 선언문
- 기준문
- 정리문
- 지시서
- 설명서
- 인계문
- 판단 메모
- 구조 메모

이 문서들에는 이미 아래가 압축되어 있다.

- 의도
- 흐름
- 맥락
- 과정
- 결과
- 범위
- 금지사항
- 다음 단계

따라서 이런 문서는 **엔진의 최상급 재료**로 취급해야 한다.

### 3.3 Codex 실행 해석
Codex 실행은 문서 재료와 분리된 별개의 일이 아니다.

정확한 해석은 아래다.

- 문서가 먼저 존재한다.
- 그 문서는 엔진 재료로 저장된다.
- 같은 문서에서 Codex 실행이 파생된다.
- 실행 결과는 다시 문서/티켓/기록과 연결된 후속 사건으로 남는다.

즉 구조는

`문서 -> Codex 실행`

이 아니라,

`문서 = 중심 재료`
`Codex 실행 = 그 재료에서 갈라지는 운영 경로`

로 읽어야 한다.

## 4. 왜 이런 선언이 필요한가
기존 방식으로는 Codex에게 넘기는 문서가 일회성 작업 프롬프트처럼 흩어지기 쉽다.
하지만 실제로는 그 문서 안에 가장 중요한 값이 이미 담겨 있다.

- 왜 이 작업을 하는지
- 어떤 구조 판단 끝에 나온 지시인지
- 무엇을 바꾸지 말아야 하는지
- 무엇을 먼저 해야 하는지
- 어떤 결과를 기대하는지

즉 이런 문서를 엔진 재료로 쓰지 않으면,
오히려 가장 고밀도의 구조 재료를 놓치는 셈이 된다.

따라서 앞으로는 생대화 전체를 무겁게 통째로 밀어 넣기보다,
**대화 중간에 생성된 구조화 문서형 산출물**을 기본 엔진 재료로 우선 취급한다.

## 5. 입력기에 대한 선언
입력기는 좁게 잠그지 않는다.

앞으로 들어올 수 있는 입력은 다양하다.

- 너와 사용자 사이에서 생성된 구조화 문서
- 회사 문서 일부
- 교육 자료
- 유튜브 원문
- LM Notebook 정리본
- 현장 메모
- 외부 비교 메모
- 실행 산출물
- status 문서
- 스크립트 / 폴더 / 결과 리포트

따라서 입력기의 선언은
“이것만 입력으로 받는다”가 아니라 아래여야 한다.

**입력기는 넓게 열어두되, 입력마다 출처/정제도/역할/우선도를 먼저 판독하여 다른 처리 레인으로 보낸다.**

단, 그 안에서
너와 사용자 사이에서 생성된 구조화 문서는
**high-grade structured material** 로 별도 마킹한다.

## 6. 운영 객체 선언
앞으로 엔진이 다루는 대상은 생각 fragment만이 아니다.

아래 모두가 엔진의 대상이 된다.

- 문서
- fragment
- label
- anchor
- ticket
- event
- script
- file
- folder
- runtime output
- report
- status document
- reference asset

즉 엔진은 “공간 속 조각”만 다루는 것이 아니라,
**운영 과정에서 생성·수정·참조되는 객체 전체를 다루는 구조**로 본다.

## 7. 역할 분리 선언
혼동을 막기 위해 아래 4개는 절대 같은 것으로 쓰지 않는다.

### 7.1 라벨
이것이 무엇인지 붙이는 값
- identity
- classification
- grouping
- retrieval handle

예:
- `directive`
- `baseline`
- `engine_component`
- `script`
- `runtime_output`
- `status_doc`

### 7.2 티켓
무엇을 해야 하는지 붙이는 값
- action
- execution
- work tracking
- progress handling

예:
- `expand_folder_status`
- `create_script`
- `review_runtime_output`

### 7.3 실행 기록
실제로 무슨 일이 일어났는지 남기는 값
- created
- updated
- executed
- generated
- failed
- compacted

### 7.4 status 문서
현재 상태를 사람이 이해하도록 압축 설명하는 문서

즉 아래처럼 고정한다.

- `label = 정체성`
- `ticket = 해야 할 일`
- `event record = 일어난 일`
- `status.md = 사람이 읽는 정리본`

## 8. 기록 방식 선언
앞으로 Codex는 매번 예쁜 markdown 문서를 직접 대규모 수정하는 방식을 기본으로 삼지 않는다.

기본 원칙은 아래다.

### 8.1 append-only first
실행이 발생하면 먼저 작은 기록을 남긴다.

예:
- 새 스크립트 생성
- 스크립트 실행
- 결과 파일 산출
- 파일 수정
- 티켓 완료
- status 반영 예정
- compaction 수행

### 8.2 compaction later
작은 기록이 충분히 쌓이면 그때 status 문서나 요약 문서로 정리한다.

즉 status 문서는 실시간 운영 로그가 아니라,
**운영 로그를 사람이 읽을 수 있게 압축한 결과**로 본다.

### 8.3 원문 보존 우선
문서 원문은 덮어쓰지 않는다.
전처리 결과는 sidecar 또는 파생 기록으로 붙인다.

## 9. 실행 흐름 선언
Codex는 앞으로 문서 입력이 들어오면 아래 순서로 이해한다.

### 9.1 문서 수신
문서 원문을 보존한다.

### 9.2 문서 마킹
문서의 역할과 재료 등급을 읽는다.

예:
- declaration
- baseline
- directive
- structured_internal_doc
- external_reference
- execution_coupled_doc

### 9.3 엔진 투입
같은 문서를 엔진 재료로 저장한다.
- fragment 분절
- role marking
- label/anchor/axis 부착 가능성 확보
- provenance 기록

### 9.4 실행 티켓화
문서에서 실행 가능한 항목을 티켓으로 분리한다.

### 9.5 Codex 실행
코드 작성, 수정, 점검, 보고서 생성, 폴더 상태 반영 등 실제 작업 수행

### 9.6 사건 기록
무슨 일이 일어났는지 append-only로 남긴다.

### 9.7 대상 메타 갱신
생성/수정된 파일, 스크립트, 결과물에 label/ticket/provenance 부착

### 9.8 나중 정리
충분한 실행 기록이 쌓이면 status 문서에 압축 반영

## 10. status 문서에 대한 선언
status 문서는 중요하다.
하지만 status 문서는 모든 것을 직접 처리하는 운영 로그여서는 안 된다.

status 문서는 아래 역할을 가진다.

- 폴더/영역의 현재 구조 설명
- 중요한 파일의 역할 설명
- 최근 중요 변경 요약
- 사람이 빠르게 전체 구조를 읽는 기준 문서

즉 status 문서는 계속 직접 손으로 흔드는 운영 장부가 아니라,
**운영 로그와 실행 흔적을 바탕으로 정리되는 상위 설명층**이다.

## 11. structured internal docs에 대한 특별 선언
너와 사용자 사이에서 생성된 구조화 문서는 별도 우선 취급한다.

이 문서들은 아래 성질을 가진다.

- 의미가 이미 응축되어 있음
- 의도/맥락/과정/결과가 함께 있음
- 전처리 부담이 낮음
- Codex 실행과 직접 연결 가능
- 엔진 input material로서 밀도가 높음

따라서 이런 문서는 아래처럼 취급한다.

- 기본 입력 허용
- high-grade structured material 표시
- 원문 우선 보존
- 최소 전처리 또는 선택적 전처리
- later ticket linkage 허용
- later result lineage 연결

## 12. 범위를 벗어나는 오해 금지
아래와 같은 오해를 금지한다.

### 오해 1
“이제 구조화 문서만 엔진에 넣는다”
- 아니다. 입력기는 넓게 열린다.
- 단지 구조화 문서를 우선 재료로 본다.

### 오해 2
“label이 status.md를 대체한다”
- 아니다.
- label/ticket은 조회 손잡이이고, status.md는 구조 설명 문서다.

### 오해 3
“모든 실행 후 바로 예쁜 md 문서를 수정해야 한다”
- 아니다.
- 먼저 작은 기록을 남기고, 나중에 compaction 한다.

### 오해 4
“Codex 실행 결과는 외부 부산물이다”
- 아니다.
- 그것도 엔진 대상이며 later lineage를 가진다.

## 13. Codex에게 요구되는 태도
앞으로 Codex는 아래 태도를 기본으로 삼는다.

1. 문서를 일회성 프롬프트로 취급하지 않는다.
2. 구조화 문서를 엔진 재료로 먼저 읽는다.
3. 실행은 사건으로 남긴다.
4. 라벨/티켓/기록/status의 역할을 섞지 않는다.
5. status 문서는 정리층으로 유지한다.
6. 원문 보존을 우선한다.
7. 입력의 폭은 넓게, 처리 방식은 차등적으로 가져간다.
8. 결과물, 스크립트, 폴더도 엔진 대상이라는 관점을 유지한다.

## 14. 최종 선언
`vectorfl_replica` 는

**생각 fragment만 담는 좁은 공간 엔진이 아니라,
구조화 문서, 외부 자료, 실행 결과, 스크립트와 폴더 같은 구성요소를 함께 받아들이고,
이를 입력-판독-실행-기록-정리의 순환 안에서 다루는 운영 엔진**으로 정의한다.

그리고 이 엔진에서
너와 사용자 사이에서 생성된 구조화 문서는
**Codex 실행을 위한 보조 텍스트가 아니라,
가장 먼저 저장되고 판독되어야 할 핵심 재료**로 선언한다.

## 15. 마지막 한 줄
앞으로 Codex는
**문서를 시키는 말로만 읽지 말고, 먼저 엔진 재료로 읽어라.
그리고 실행은 작은 사건 기록으로 남기고, status는 나중에 정리하라.**
